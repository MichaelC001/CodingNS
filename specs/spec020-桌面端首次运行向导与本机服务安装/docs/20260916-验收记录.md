## 任务 1.4 向导入口判定与路由

对应设计：`design.md` §2.4.1（向导入口判定），对应需求 1。要按固定顺序判断这次启动是走正常流程还是进向导。

### 改了什么

| 文件 | 改动 |
| --- | --- |
| `apps/user-app/src/features/setup/onboarding-entry.ts`（新增） | 判定逻辑：先做能拍板的同步判定，需要等扫描时再异步等（最多 2.5 秒），另含补记完成标记 |
| `apps/user-app/src/features/setup/components/OnboardingEntryGuard.tsx`（新增） | 路由守卫：判定期间渲染轻量占位；判定结果是"要进向导"时跳 `/setup` |
| `apps/user-app/src/features/setup/pages/SetupWizardPage.tsx`（新增） | 向导占位页，真实内容留给任务 2.1 |
| `apps/user-app/src/app/router.tsx` | 新增 `/setup` 路由；登录、bootstrap、工作台这些入口挂到守卫下；中继连接页和桌面窗口预览不挂守卫（避免打断独立流程） |
| `apps/user-app/src/i18n/zh-CN.ts`、`en-US.ts` | 新增 `setup` 段两条文案 |

判定顺序：

1. 非桌面端 → 正常流程；
2. 有 `onboardingCompletedAt` → 正常流程；
3. 有连接历史（host profile 的 `lastConnectedAt` 非空）→ 正常流程，并补记完成标记；
4. 已经扫到可达的本机服务 → 先连过去，再补记完成标记；
5. 扫描还没结果 → 最多等 2.5 秒；等到了就连过去，等不到按第 6 步；
6. 其余 → 进 `/setup`。

判定期间渲染的是和启动页一致的轻量占位，不等网络、不阻塞首屏。

## 阶段 3 验收记录（任务 3.1 - 3.3：统一安装器）

安装器是 `packages/codingns/scripts/host-install.mjs`，零外部依赖，只 import `node:` 内置模块。桌面端向导和 `install.sh` 共用这一份。

### 3.1 骨架与只读动作

搭出参数解析、JSON Lines 输出、日志落盘、退出码约定，实现 `check` 和 `status`。

**手工验证**

```
$ node packages/codingns/scripts/host-install.mjs check --data-dir <空目录>
{"type":"step","stepId":"check-install-state","status":"running", ...}
{"type":"step","stepId":"check-install-state","status":"done", ...}
{"type":"result","data":null}
exit=0

$ （放一份 install-state.json 后再跑）
{"type":"result","data":{"schemaVersion":1,"packageVersion":"2.1.0", ...}}
exit=0

$ node packages/codingns/scripts/host-install.mjs status --data-dir <同一目录>
{"type":"result","data":{"dataDir":"...","installed":true,"running":true,"pid":909,"port":3002, ...}}
exit=0

$ node packages/codingns/scripts/host-install.mjs launch
{"type":"error","code":"UNKNOWN_ACTION","message":"不认识的安装器动作：launch","detail":null,"logPath":null}
```

## Windows 上安装器启动即崩：`\\?\` 路径前缀（2026-09-16 修复）

**现象**：Windows 上点「重新安装」，安装器一行日志都没写就退出，界面里只有 node 自己的崩溃：

```
Error: EISDIR: illegal operation on a directory, lstat 'C:'
    at Object.realpathSync (node:fs:2806:25)
    at Module._findPath (node:internal/modules/cjs/loader:850:22)
    at resolveMainPath (node:internal/modules/run_main:35:21)
```

**原因**：Tauri 算 `resource_dir()` 时内部走的是 Rust 的 `canonicalize()`，Windows 上得到的是 `\\?\C:\...` 这种长路径形式。我们拿它拼出安装器入口，直接交给了 node。Node 22.20 之后对带 `\\?\` 前缀的入口有已知回归（nodejs/node#60435），解析入口时会把路径错认成盘符 `C:`，于是启动阶段就崩掉——所以安装器连第一行日志都没来得及写。

**改法**：凡是交给 node 的路径，先去掉 `\\?\` 前缀。

| 位置 | 改动 |
| --- | --- |
| `node_runtime.rs` | 新增 `to_node_path()`，顺带把 `\\?\UNC\server\share` 还原成 `\\server\share` |
| `host_installer.rs` | 安装器脚本路径、数据目录在返回前归一化 |
| `host_setup.rs` | 环境探测返回的数据目录归一化 |
| `host-install.mjs` | 新增 `normalizeNodePath()`，`spawnDetachedHost` 与三个自启文件生成都走它 |

**为什么之前没发现**：macOS 上 `canonicalize()` 不产生这种前缀，本地验证全绿；这个崩溃只在 Windows 真机出现。

**本轮验证**：`cargo test --lib` 55 通过（新增 2 个归一化单测）；`node --test tests/host-install.test.mjs` 35 通过（新增 2 个）。Windows 真机复验还没做。

## Windows 真机上又发现两个问题（2026-09-16，用户贴出安装器日志后定位并修复）

用户装了修完 `\\?\` 的包，向导能跑到"正在安装服务"了，但卡在装包这一步。日志里两行关键内容（PowerShell 显示成乱码，实际是 UTF-8 日志被按 GBK 读）：

```
执行 npm 命令 :: C:\WINDOWS\system32\cmd.exe /d /s /c C:\Program Files\nodejs\npm.cmd install --global --prefix ... --registry https://registry.npmjs.org
执行 npm 命令 :: C:\WINDOWS\system32\cmd.exe /d /s /c C:\Program Files\nodejs\npm.cmd install --global --prefix ... --registry https://registry.npmmirror.com
npm 安装结束 :: [{"registry":"https://registry.npmjs.org","ok":false,"status":1,"detail":"'C:\\Program' 不是内部或外部命令…"}, {...npmmirror 同样失败...}]
```

### 问题一（拦路的那一个）：npm 路径没加引号，cmd.exe 在空格处断开

两次"换源重试"只隔 22 毫秒，而且报的是 `'C:\Program' 不是内部或外部命令` —— **根本没走到网络**，第一个空格就把命令拆了：`C:\Program Files\nodejs\npm.cmd` 被 cmd.exe 当成 `C:\Program`。

根子在 `runNpmCommand`：Windows 上拼的是 `cmd.exe /d /s /c <npmPath> <args>`，而 `cmd /s /c` 会把带空格的路径外层引号吃掉再按空格切分。Node 装在 `C:\Program Files\nodejs`（官方 MSI 的默认位置）时必炸。

**跟镜像源、跟网络都没有关系**——这也是"两个源都失败"的真实原因。

**改法**：Windows 上不再经过 cmd.exe，改用当前 node 直接跑 npm 的 JS 入口（`<nodeDir>/node_modules/npm/bin/npm-cli.js`），既绕开 shell 的引号规则，也让 npm 输出走 UTF-8（cmd.exe 在中文系统上吐 GBK，这正是日志变乱码的来源）。找不到这个 JS 入口时退回 cmd，但整条命令行会再包一层引号并用 `windowsVerbatimArguments` 交给系统，`C:\Program Files\...` 不会再被拆开。

| 位置 | 改动 |
| --- | --- |
| `host-install.mjs` | 新增 `resolveNpmInvocation()`：Windows + `.cmd/.bat` → 优先 `node npm-cli.js`，退路才走 cmd 且整体加引号；`runNpmCommand` 按它执行 |

**验证**（`node --test packages/codingns/tests/host-install.test.mjs`，38 通过）：

```
Windows 上优先用 node 直跑 npm 的 JS 入口，不经过 cmd.exe ... ok
找不到 npm-cli.js 时退回 cmd，并把带空格的路径整体包进引号 ... ok
非 Windows 直接执行 npm，不做中转 ... ok
```

三条分支的实际拼装结果（本机跑真函数）：

```
primary : C:\Program Files\nodejs\node.exe | C:\Program Files\nodejs\node_modules\npm\bin\npm-cli.js install --global
fallback: cmd.exe | /d /s /c ""C:\Program Files\nodejs\npm.cmd" install --global"
posix   : /usr/local/bin/npm | install
```

改完在本机重跑了一遍完整往返（临时数据目录 + 端口 4199 + 本地 tarball）：安装成功 → `curl` 拿到 HTTP 200 → 停止 → `uninstall --purge` 清干净。**npm 调用这条路径没有回归。**

### 问题二：具体错误被"退出码 1"盖掉了

界面详情里只有 `INSTALLER_FAILED / 退出码 1`，看不到 npm 的原文。原因是安装器**已经**用 `NPM_INSTALL_FAILED` 把事情说清楚了（detail 里就是 npm 的报错），进程随后非零退出，Rust 又补发了一条 `INSTALLER_FAILED`（detail 只有退出码），把前面那条更具体的覆盖掉了。

**改法**：只在安装器没自己报过错的时候才补 `INSTALLER_FAILED`；已经报过错的情况下，stderr 尾巴降级成一条日志，不再覆盖失败原因。

| 位置 | 改动 |
| --- | --- |
| `host_installer.rs` | 读 stdout 时记下是否出现过结构化 `error`；新增纯函数 `should_report_installer_failure(exit_success, saw_structured_error)` 决定要不要补退出码错误 |

**验证**：`cargo test --lib host_installer::` 7 通过，含新增的 `keeps_the_specific_error_instead_of_exit_code_noise`。

### 这两个问题的共同教训

三条探测路径（网络、镜像、Node 版本）当时全都怀疑过，真因却是**命令行拼装**这种纯本地问题。所以"日志里贴出实际执行的命令"（`执行 npm 命令 :: ...`）这一步是值得的——正是它一眼暴露了空格没转义。Windows 特有、macOS 上永远复现不了的这一类问题，只能靠真机日志定位。

### 还没验证的

1. 这两个修复需要**重新打包 Windows 版**才能复验，本轮只在 macOS 上验证了逻辑与回归。
2. 顺带说一句：日志文件本身是 UTF-8，用 PowerShell 5.1 的 `Get-Content` 看会显示成乱码，要加 `-Encoding UTF8`（PowerShell 7 默认就对）。界面里的详情不受影响。

## 装服务时弹出的黑窗口与"看不到进度"（2026-09-16，用户贴出向导截图后修复）

用户装服务时截图显示：向导停在"安装服务"这一步没动静，前面却弹出一个黑窗口，标题是 `npm install @jingyi0605/codingns`。两个问题——外部窗口不该出现，进度也不该只活在那个窗口里。

| `host_installer.rs` | 跑安装器、读安装状态、`taskkill` 收进程树 |
| `node_runtime.rs` | `node -v` 版本检查、`where/which node`、解压用的 `tar`、`powershell` |
| `host_setup.rs` | 环境探测命令 |
| `host_discovery.rs` | `ps` / `powershell` 进程扫描 |

`file_system.rs`（打开文件夹）、`rollback.rs` / `updater.rs`（拉起安装包、打开链接）保持原样——这些本来就是要弹给用户看的。

### 问题二：npm 的输出没有进向导

上限：最多转发 120 行、每行 240 字符，避免 npm 刷屏把界面顶爆；失败详情仍取完整的 stderr。

**验证**：

## 重新安装时 npm 报 EBUSY：安装目录被旧服务占着（2026-09-16）

用户在新包里已经能看到 npm 原文了，报的是换源完全无效的一类错误：

```
npm error code EBUSY
npm error syscall rename
npm error path C:\Users\admin\.codingns\runtime\npm\node_modules\@jingyi0605\codingns
npm error dest C:\Users\admin\.codingns\runtime\npm\node_modules\@jingyi0605\.codingns-CIU3aYFP
npm error errno -4082
npm error EBUSY: resource busy or locked, rename '...\@jingyi0605\codingns' -> '...\.codingns-CIU3aYFP'
```

两次换源报的是同一个错误、同一个 `.codingns-CIU3aYFP` 目标名，说明和网络无关。

### 真因：上一份服务还在跑

报错路径里的包目录说明**上一次安装是成功的**，服务已经在跑。这次重新安装时 npm 要把旧目录挪走（rename 到 `.codingns-<随机后缀>`），而 Windows 不允许挪动正被进程占用的目录。

占用来源有两处，都在我们自己身上：

1. 运行中的服务进程，进程里加载着这个目录下的 JS 和原生模块（better-sqlite3 这类是 DLL，加载后一直占着文件）；
2. `spawnDetachedHost` 把服务进程的**工作目录**设成了安装包目录 —— Windows 上子进程的 cwd 会把整个目录钉住。这条是上一版遗留，第一次装没事，第二次装才炸。

顺带发现一个更隐蔽的问题：**旧服务不停，新进程抢不到端口**，而健康检查连上的其实是旧进程，会「通过」——也就是升级看着成功、实际还跑着旧代码。

### 改法

| 位置 | 改动 |
| --- | --- |
| `runInstall` | 装包前先 `stopRunningHost`（按数据目录 / 端口认进程），日志里写明停掉的 pid；装完照旧重新拉起 |
| `runInstall` | npm 报 EBUSY 时不再换镜像源（换也没用）：停掉占用者、等 2 秒让文件句柄释放，再用**同一个源**重试一次 |
| `spawnDetachedHost` | 工作目录从安装包目录改到数据目录（新增 `resolveHostWorkingDirectory`） |
| `install.sh` | 它自己那次 `npm install -g` 跑在统一安装器之前，装包前也 best-effort 停一次服务（停不掉不拦着安装） |

### 验证

```
node --test packages/codingns/tests/host-install.test.mjs
# tests 44 / # pass 44 / # fail 0
  ok - 装包之前先停掉正在运行的服务
  ok - npm 报 EBUSY 时停掉占用者、用同一个源重试，而不是换镜像源
  ok - EBUSY 重试仍然失败时给出占用提示，而不是让用户去查网络
  ok - 服务进程的工作目录是数据目录，不是安装包目录

bash -n install.sh   # 语法检查通过
```

测试辅助函数里把进程探测换成了桩（`detectRunningHost` 默认返回 null）：既快，也避免测试误杀开发机上正在跑的服务。

### 还没验证的

1. **真机复验**：要验证这条修复，需要「先装好一版并让它跑起来 → 再跑一次向导」，本轮只在 macOS 上用桩覆盖了逻辑分支。
2. 极端情况仍可能失败：杀毒软件扫描、资源管理器预览、用户手工起的服务占着目录时，重试一次还会失败——这种情况下界面会明确提示「安装目录一直被占用」，不再引导用户去查网络或换源。

## 一次弹出十几个黑窗口 + 开机自启启用失败（2026-09-16）

用户反馈：安装到「启用开机自启」这一步失败，同时屏幕上叠了一排黑窗口，标题全是 `C:\Program Files\nodejs\node.exe`。

### 黑窗口的真因：服务进程没有控制台，子进程各自开窗

`spawnDetachedHost` 在 Windows 上用 detached 启动服务进程，对应 `DETACHED_PROCESS`：**服务进程没有控制台**。没有控制台的进程再拉起控制台子进程时，系统会给每个子进程单独分配一个新控制台——也就是每拉一个就弹一个黑窗口，一次能弹十几个。

**改法**：黑窗口在**子进程侧**修——`apps/host` 里三个启动阶段就会拉起的 helper 之前漏了 `windowsHide`（仓库里其它 spawn 都有）：

| 位置 | 改动 |
| --- | --- |
| `task-helper-client` / `provider-discovery-helper-client` / `opencode-system-probe-helper-client` | 三处 spawn 补上 `windowsHide: true` |
| `listWindowsHostProcesses` | 探测进程用的 PowerShell 之前没加 `windowsHide`，也会闪窗，补上 |

**走过的弯路（记下来，别再来一遍）**：一开始试图让服务进程「Windows 上不 detached」，想给它一个存在但不可见的控制台。

> 真机结果：**服务进程会跟着安装器一起退出**——装完那一下健康检查是通的，安装器一退出服务就没了，客户端马上显示「连不上这台电脑上的服务」。
> 也就是说 detached 在 Windows 上不是可选项：它是服务进程能活过安装器的那根线。已回退，并在代码里写明原因。

这条弯路还有个教训：**别再用「理论推断」改 Windows 上的进程启动参数**，本地 macOS 压根测不到这类差异；要么有真机结论，要么先在 CI 上做出可判定的用例。

### 开机自启失败：schtasks 建任务被拒，但没有退路

`activateAutostart` 在 Windows 上只走一条路：`schtasks /Create /SC ONLOGON`。这条命令在用户的机器上被拒（计划任务需要权限、被组策略拦、或任务计划服务被禁用都可能），于是整个安装被判失败——**服务其实已经装好并且在跑了**，用户看到「安装没成功」很冤。

**改法**：

| 位置 | 改动 |
| --- | --- |
| `activateAutostart` | `schtasks` 失败时退到**启动文件夹**（`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\CodingNS Host.vbs`），写的是同一个静默启动脚本（VBS 里窗口模式 0）；两条路都失败才报 `AUTOSTART_FAILED`，失败详情里同时带上 schtasks 原文和启动文件夹的报错 |
| `deactivateAutostart` | 关闭自启时计划任务和启动文件夹两边都清，避免留残 |
| `runAutostart` / `runInstall` | 结果里的 `autostartKind` / `autostartPath` 记**实际生效**的方式，不再固定写准备时的那个 |
| `runInstall` | 失败文案改成「开机自启没启用成功（服务本身已经装好并且在运行）」，避免用户以为整件事都失败了 |

**这是对 design.md 的一处偏离**：设计里 Windows 只写用户计划任务，现在多了一条启动文件夹兜底路径。design.md 没有改动，按约定先在这里说明。

### 验证

## 装完之后「看不到服务是否启动」（2026-09-16）

用户真机反馈：向导装完直接跳到登录页，登录页写「连不上这台电脑上的服务」，看不出服务到底起没起；同时贴出了安装日志。

### 日志说明装其实是成功的

安装日志（真机，Windows）里这些都对：npm 装上 2.1.0、健康检查 10 秒后通过、自启退回启动文件夹、安装状态落盘（`autostartKind: "startup-folder"`）。也就是说「装」这一段已经跑通，问题在**装完之后客户端能不能连上、以及连不上时能不能说清楚原因**。

### 两个改动

**1. 服务进程的输出终于有地方看了**

`spawnDetachedHost` 之前是 `stdio: "ignore"`，服务启动阶段崩掉时一行线索都没有，只能看到健康检查超时。现在 stdout/stderr 落到 `<数据目录>/runtime/logs/host-service.log`，日志行里也带上这个路径。
（自启那份 VBS 仍不重定向输出，登录后自启起的服务还是看不到输出，这条留着以后一起改。）

**2. 「连不上」旁边直接给出原因**

`probeHost` 原来把异常吞掉只回 `reachable: false`，界面就一句「连不上」，分不清是服务没起来、还是浏览器跨源把请求拦了、还是服务返回了错误码。现在把原因带到空态卡片上：

| 情况 | 界面上看到的失败原因 |
| --- | --- |
| 服务没起来 / 端口没人监听 | `Failed to fetch`（浏览器原文） |
| 服务返回错误码 | `HTTP 503：服务正在升级` |
| 其它异常 | 异常原文 |

### 顺带修的：三个 helper 子进程弹黑窗

`apps/host` 里 `task-helper-client`、`provider-discovery-helper-client`、`opencode-system-probe-helper-client` 三处 spawn 少了 `windowsHide`（仓库里其它 spawn 都有）。服务进程没有自己的控制台，这三个 helper 又都在启动阶段拉起，正好对上用户看到的「一次弹一排 node.exe 黑窗」。

### 验证

```

pnpm --dir apps/host test tests/integration/task-helper-client.test.ts \
  tests/integration/provider-discovery-helper-client.test.ts  # 12 pass
pnpm --dir apps/user-app test src/features/auth/pages/LoginPage.host-empty-state.test.tsx  # 11 pass
npx tsc --noEmit                                              # 通过
```

### 这一轮同时纠正的：上一版把 detached 去掉是个回归

用户这次的日志里「健康检查通过 → 安装器退出 → 客户端连不上」，对着代码看就是上一版改动造成的：
本意是治黑窗口，实际把服务进程的存活条件砍了。本轮已回退（见上文「走过的弯路」）。
黑窗口改由子进程侧 `windowsHide` 负责，这一版才是正确的分工。

### 还没定论的

**回退之后服务还会不会掉，要等真机再看一次。** 空态卡片上的 `localHost` 分支用的是「扫描到的本机服务」，而它会把已经存成正式 HOST 的同一个地址过滤掉，所以「连不上」这张卡片并不能证明服务不在跑。要确认只需要在真机上执行：

```powershell
Get-NetTCPConnection -LocalPort 3002 -State Listen -ErrorAction SilentlyContinue |
  Select-Object -First 1 LocalAddress,OwningProcess | Format-List
```

- 有输出 → 服务在跑，问题在前端连不上它（跨源、CSP、地址）；
- 没输出 → 服务真的退了，这时到 `<数据目录>\runtime\logs\host-service.log` 看崩溃现场。

## 装成功了，但建自启那一步又弹一叠黑窗（2026-09-16）

用户真机反馈：**这次安装成功了**（向导走完，客户端停在「先完成首次初始化」），但「创建计划任务的时候」又出现一叠黑窗，标题全是 `C:\Program Files\nodejs\node.exe`。

### 为什么上一轮的 helper 修复没生效

上一轮给 `apps/host` 里三个 helper 补了 `windowsHide`，但那三个文件属于**服务包**（`@jingyi0605/codingns`），是向导从 npm 装的；用户机器上的服务还是线上的 2.1.0，里面没有这个修复。也就是说：**服务侧的修复不发新版本就到不了用户机器上**。

### 这一轮改成在启动层解决

服务进程是被一个没有控制台的父进程拉起来的（detached + 安装器本身也没有控制台），Windows 让它一路都没有控制台；它再拉起 helper、git、终端这些控制台子进程时，系统会给**每个**子进程单独开一个新控制台——就是用户看到的这一叠。

改法：服务改走 **0 号窗口模式的 VBS 包装**启动（这份包装本来就有，自启一直用它）：

| 关注点 | 做法 |
| --- | --- |
| 黑窗 | `shell.Run ..., 0, False` 给服务一个「有控制台、窗口隐藏」的进程，子进程继承它，不再各自开窗 |
| 文件分工 | 命令和重定向写进 `codingns-host-launcher.cmd`，`codingns-host-launcher.vbs` 只负责用 0 号窗口模式拉起它 |
| 日志 | 批处理里一行 `... >> "host-service.log" 2>&1`，stdout 和 stderr 一起收 |
| 兜底 | 包装写不出来、或包装起不来（健康检查超时）时，退回直接拉 node：窗口难看总好过服务起不来 |
| 停服 | 进程扫描按命令行认服务，包装多出来的 `cmd.exe` / `wscript.exe` 不在 `node.exe` 里，认不到也不影响 |

**中途翻的车**：一开始把命令拼成 `cmd /d /s /c ""..."" >> "..." 2>&1`（那套「外层再加一对引号」的标准写法），CI 上直接报
`The filename, directory name, or volume label syntax is incorrect.`——外层引号在真机上就是不稳。改成批处理之后引号只出现在一行普通命令行里，CI 一次通过。

**引号改动还顺带带来两件事**：一是日志目录必须先建出来，否则 `>>` 会整条命令失败（CI 抓到过一次）；二是 `wscript` 那条路跑的服务，输出现在也进 `host-service.log` 了，以前是直接丢掉的。

顺带修掉一个真问题：服务日志路径带 `\\?\` 前缀时会被写进 VBS 交给 cmd，cmd 解释不了——现在统一去掉前缀（单测抓到的）。

### 这次不敢只靠推理

上一轮「Windows 上不 detached」就是靠推理改的，真机上直接把服务搞死了。所以这次加了构建前的 Windows 验证步骤 `scripts/verify-windows-host-launcher.mjs`：

1. 写一个假服务（打印 stdout、stderr，1.5 秒后再打印一行，然后常驻）；
2. 走产品自己的 `ensureWindowsHostLauncher` 把包装写出来（顺便验它建日志目录这步）；
3. 用 `wscript.exe` 真拉起包装；
4. 断言 `host-service.log` 里同时有 stdout、stderr 和 1.5 秒后那一行，并且服务进程还活着。

结果（run [35088433524](https://github.com/jingyi0605/CodingNS/actions/runs/35088433524)，Windows 构建，构建前步骤）：

```
启动包装验证通过：
- 日志：...\data\runtime\logs\host-service.log
- 内容：FAKE-SERVICE-STDOUT | FAKE-SERVICE-STDERR | FAKE-SERVICE-STILL-ALIVE
- 服务进程 pid 7408 仍然存活
```

窗口有没有真的藏住只能真机看，这一步验不了。

### 还没做的

1. **服务包的版本问题没解决**：用户机器上的服务永远来自 npm registry，客户端换多少版都追不上它。要么发新版本，要么让桌面端改装自带的包（更彻底，客户端和服务不会再漂），两条都需要确认。
2. **登录时自启还没验过**：包装内容变了（多了 cmd 重定向），自启走的是同一份包装，得等一次真正的登录或重启。
3. 真机上黑窗是否真的消失、服务是否还在：等这一版回执。
