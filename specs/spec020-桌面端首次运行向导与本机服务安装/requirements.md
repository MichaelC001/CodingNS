# 需求文档 - 桌面端首次运行向导与本机服务安装

状态：Draft

## 简介

### 当前是什么情况

CodingNS 现在分成两半，各自独立安装：

- **服务端（Host）**：通过 npm 包 `@jingyi0605/codingns` 安装，命令行执行 `codingns start` 运行，`install.sh` 负责装依赖、托管进程和配开机自启。
- **桌面客户端**：Tauri 应用，从 GitHub Release 下载 dmg / exe 安装。它自己不带 Node，也不带服务端，启动后只是扫描本机有没有正在跑的 Host 进程，然后连上去。

问题出在两者之间没有任何衔接。一个新用户下载安装了桌面客户端，双击打开，**看到的是一个没有任何提示的界面**：本机没有服务，探活失败只返回"不可达"而不报错，所以页面上既没有错误也没有引导，用户只能看到一个连不上的登录页。他必须自己去搜索引擎找 `install.sh`，学会用命令行装一遍服务端，再回来打开客户端。

这条路对非技术用户基本走不通。

### 这次要做什么

给桌面客户端加一个**首次运行向导**，让用户在图形界面里完成原本要靠命令行做的事：

- 选择这台电脑的用途：只当客户端（连别人），还是本机装服务（当服务端）
- 当客户端：填地址直连，或通过 CodingNS 中继连接，并且当场测试通不通
- 当服务端：在界面里装好本机服务，设置端口、数据目录、开机自启，装完自动连上

同时把安装服务这件事抽成一份**跨平台的安装脚本**，桌面端和 `install.sh` 共用同一份逻辑，避免出现两套互相不认识的安装方式。

### 服务哪些角色

- **普通用户**：下载桌面客户端后，不需要碰命令行就能把整套东西跑起来。
- **已有服务端的用户**：桌面端只是连过去，向导应该安静地跳过，不打扰。
- **命令行 / 服务器用户**：继续用 `install.sh`，并且可以选择顺手把桌面客户端也装上。

### 成功后的收益

从"下载客户端 → 能用"之间不再有命令行断点。装机、配端口、配自启这些事第一次就可以在界面里做完。

## 术语表

- **Host（服务端）**：CodingNS 的后端服务，一个 Node 进程，默认监听 3002 端口，桌面端和手机端都连它。
- **桌面端（客户端）**：`apps/desktop`，Tauri 打包的桌面程序，本身不含 Node 和服务端代码。
- **向导**：本 Spec 新增的首次运行引导界面，路由 `/setup`。
- **原生自启**：用操作系统自带的开机启动能力拉起 Host。macOS 用 LaunchAgent，Linux 用 systemd user service，Windows 用计划任务。不使用 pm2。
- **安装器**：本 Spec 新增的跨平台 Node 脚本，负责装服务端、配自启、启动和自检。桌面端和 `install.sh` 都调它。
- **私有运行时**：装在用户目录下的 Node 和 npm 全局目录（`~/.codingns/runtime/`），不需要管理员权限，不污染系统环境。
- **直连**：客户端直接访问 Host 的地址，例如 `http://192.168.1.10:3002`。
- **中继连接**：客户端通过 CodingNS 中继服务访问 Host，用 `<域名>.channel.codingns.com` 这种地址，适合 Host 没有公网 IP 的情况。

## 范围说明

### In Scope

- 桌面端首次运行的角色选择向导（客户端 / 服务端）
- 客户端模式的两种连接方式引导：直连、中继
- 服务端模式的本机安装引导：环境检测、参数设置、安装进度、装完自动连接
- 桌面端连不上服务时的首屏引导（替换现在的无提示白屏）
- 一份跨平台安装器脚本，桌面端与 `install.sh` 共用
- 桌面端下载并准备私有 Node 运行时的能力
- macOS / Linux / Windows 三平台的原生开机自启配置
- `install.sh` 接入统一安装器，并新增"顺便安装桌面客户端"选项

### Out of Scope

- 不把桌面客户端打包进 npm 包。这一条已明确否决。
- 不做"桌面安装包内置 Node 和完整服务端"的一体化安装包。这会破坏现有签名流程并让安装包膨胀到 100MB 以上。
- 不改 Host 的业务逻辑、接口协议和数据库结构。
- 不做账号注册、登录流程本身的改动，向导结束仍然进入现有登录页。
- 不替用户自动升级已有 Host，升级仍走现有服务更新链路。
- 不做移动端（iOS / Android）的对应引导。

## 需求

### 需求 1：首次运行的角色选择

**用户故事：** 作为第一次打开桌面客户端的用户，我希望它问我这台电脑要用来做什么，以便我不用先搞懂"服务端"和"客户端"的区别再自己去猜该装什么。

#### 验收标准

1. WHEN 桌面端启动且本机没有可连接的服务、配置里也没有完成过向导的记录 THEN System SHALL 进入向导第一步，展示"这台电脑要怎么用"的角色选择。
2. WHEN 向导展示角色选择 THEN System SHALL 提供两个选项："连接到已有的服务"和"在这台电脑上安装服务"，并用普通用户能看懂的一句话解释各自含义。
3. WHEN 本机扫描到已有可连接的 Host 服务 THEN System SHALL 在角色选择上方额外展示一张"检测到本机已有服务"的卡片，并提供一键连接按钮。
4. WHEN 用户点击右上角"跳过" THEN System SHALL 记录向导已完成并进入登录页，且本次会话内不再弹出向导。
5. WHEN 桌面端启动且配置里已有完成过向导的记录 THEN System SHALL 直接进入正常流程，不展示向导。
6. WHEN 用户已有历史连接记录（存在 host profile 且最近连接时间不为空）但尚未有向导完成记录 THEN System SHALL 自动补记向导完成并直接进入正常流程，不打扰老用户。
7. WHEN 用户已经完成过向导（例如连的是远程服务），之后想在这台电脑上也装一个服务 THEN System SHALL 允许从设置页重新进入向导的服务端分支，且不得重置已有的连接配置和 host profile。

### 需求 2：客户端模式的连接引导

**用户故事：** 作为已经有服务端在别处跑的用户，我希望在向导里填一次地址就能连上，并且当场知道填得对不对，以便不用来回试错。

#### 验收标准

1. WHEN 用户在角色选择里选择"连接到已有的服务" THEN System SHALL 进入连接方式选择步骤，提供"直接连接"和"通过 CodingNS 中继连接"两个选项。
2. WHEN 用户选择"直接连接" THEN System SHALL 展示地址输入框，接受 `http://主机:端口` 形式，并在提交前做格式校验。
3. WHEN 用户选择"通过 CodingNS 中继连接" THEN System SHALL 展示中继域名输入框，接受 `<域名>.channel.codingns.com` 形式，并使用项目内置的中继控制站地址。
4. WHEN 用户填完地址点击"测试连接" THEN System SHALL 真实发起一次连通性探测，并在 10 秒内给出成功或失败结果。
5. WHEN 测试连接成功 THEN System SHALL 允许进入下一步，并把该地址写入 host profile。
6. WHEN 测试连接失败 THEN System SHALL 展示失败原因（地址无法访问 / 服务未响应 / 地址格式错误）并保留已填内容，允许修改后重试。
7. WHEN 用户完成客户端分支 THEN System SHALL 记录向导完成并跳转登录页，且该连接在登录页已被选中。

### 需求 3：服务端模式的一键安装

**用户故事：** 作为想把服务装在自己电脑上的用户，我希望点几下就能装好并跑起来，以便不用打开终端敲命令。

#### 验收标准

1. WHEN 用户在角色选择里选择"在这台电脑上安装服务" THEN System SHALL 先执行环境检测，再展示参数设置步骤，两个步骤都不得在用户点击前擅自开始安装。
2. WHEN 环境检测完成 THEN System SHALL 展示：操作系统与架构、Node 运行时状态（已有可用版本 / 将自动下载的版本与体积）、是否已存在 CodingNS 服务安装、目标端口是否被占用。
3. WHEN 检测到本机已经安装过 CodingNS 服务 THEN System SHALL 提示"已安装"并允许用户选择复用现有安装或重新安装，默认复用。
4. WHEN 用户确认开始安装 THEN System SHALL 依次执行：准备 Node 运行时、安装 CodingNS 服务包、写入开机自启配置、启动服务、验证服务可访问，并把每一步的进行状态实时展示给用户。
5. WHEN 安装成功 THEN System SHALL 自动把本机服务写入 host profile、记录向导完成、跳转登录页，且登录页指向本机服务地址。
6. WHEN 安装过程中某一步失败 THEN System SHALL 停止后续步骤、展示失败步骤与可读的失败原因，并提供"重试"和"查看详情"。
7. WHEN 用户点击"取消" THEN System SHALL 在 5 秒内终止安装进程，并清理本次已产生的临时文件；已完成的服务包安装不自动回滚，但不得写入自启配置。
8. WHEN 安装过程中用户关闭窗口或退出应用 THEN System SHALL 不留下半完成的自启配置（自启配置必须是安装流程的最后一步可选项，且在服务可访问之后才写入）。

### 需求 4：服务端参数设置

**用户故事：** 作为装服务的用户，我希望自己决定端口、数据放哪、要不要开机自启，以便服务能按我的网络环境和使用习惯工作。

#### 验收标准

1. WHEN 用户进入参数设置步骤 THEN System SHALL 提供以下可配置项：访问端口（默认 3002）、数据目录（默认 `~/.codingns`）、是否开机自动启动（默认开启）、是否允许局域网内其他设备访问（默认开启）。
2. WHEN 用户修改端口且该端口已被占用 THEN System SHALL 在提交前提示端口不可用，并建议一个可用端口。
3. WHEN 用户为非默认端口或非默认数据目录 THEN System SHALL 在后续安装中确实按用户填写的值执行，不得静默回退到默认值。
4. WHEN 用户选择数据目录 THEN System SHALL 通过桌面端原生目录选择器选择，并展示所选路径。
5. WHEN 用户关闭"允许局域网内其他设备访问" THEN System SHALL 让服务只监听 `127.0.0.1`。
6. WHEN 用户关闭"开机自动启动" THEN System SHALL 完成安装并启动服务，但不写入任何自启配置。

### 需求 5：连不上服务时的首屏引导

**用户故事：** 作为打开客户端但连不上服务的用户，我希望页面直接告诉我为什么连不上、下一步该点哪里，以便我不至于对着一片空白发呆。

#### 验收标准

1. WHEN 桌面端已跳过或完成向导，但当前 host profile 探测不可达 THEN System SHALL 在登录页展示明确的空态区域，说明"连不上这台电脑上的服务"，而不是只显示一个无法使用的登录表单。
2. WHEN 展示该空态 THEN System SHALL 提供两个动作："在这台电脑上安装服务"（跳转向导的服务端分支）和"改用其他服务地址"（打开服务器地址设置）。
3. WHEN 本机扫描发现了可达的 Host 服务 THEN System SHALL 优先提供"连接这台电脑上的服务"的一键动作，而不是让用户去装。
4. WHEN 该空态出现 THEN System SHALL 不因探测失败而阻塞页面其余部分渲染，首屏必须在 3 秒内可见。

### 需求 6：install.sh 接入统一安装器

**用户故事：** 作为习惯用命令行的用户，我希望 install.sh 和桌面端用的是同一套安装逻辑，以便两边装出来的服务行为一致，出问题时排查方式也一致。

#### 验收标准

1. WHEN `install.sh` 执行到安装服务、配置自启、启动服务这些步骤 THEN System SHALL 调用统一安装器脚本完成，而不是自己再实现一遍。
2. WHEN `install.sh` 调用统一安装器 THEN System SHALL 传入用户在命令行流程里选定的端口、数据目录和自启开关。
3. WHEN `install.sh` 运行在 Windows 的 Git-Bash 环境 THEN System SHALL 通过同一份安装器完成自启配置，补上当前 Windows 侧完全没有开机自启的缺口。
4. WHEN `install.sh` 在 macOS 或 Linux 上运行 THEN System SHALL 不再依赖 pm2 完成自启；已有 pm2 托管的旧安装 SHALL 被识别并提示用户，不静默产生第二个服务进程。
5. WHEN 用户选择"顺便安装桌面客户端" THEN System SHALL 按当前平台下载对应的桌面安装包并完成安装：macOS 挂载 dmg 并复制 `.app`，Windows 静默运行安装程序。
6. WHEN 桌面客户端安装失败（下载失败、无权限、校验不通过） THEN System SHALL 明确提示失败原因，且不影响已经装好的服务端。

## 非功能需求

### 非功能需求 1：性能

1. WHEN 桌面端冷启动 THEN System SHALL 在 3 秒内渲染出首屏，环境检测和网络探测不得阻塞首屏。
2. WHEN 向导进入环境检测步骤 THEN System SHALL 在 5 秒内返回检测结果；超过 5 秒的单项检测 SHALL 以"检测中"状态异步返回，不阻塞其他项展示。
3. WHEN 安装服务 THEN System SHALL 在有网络的前提下面向用户展示进度，单步无输出超过 20 秒 SHALL 展示"仍在进行"而不是看起来卡死。
4. WHEN Node 运行时需要下载 THEN System SHALL 展示下载进度与总体积，不得只展示一个转圈图标。

### 非功能需求 2：可靠性

1. WHEN 安装过程中任一步骤失败 THEN System SHALL 保留完整日志到数据目录下的 `runtime/logs/`，并允许用户在界面上查看。
2. WHEN 安装被取消或中断 THEN System SHALL 在下次进入向导时正确识别半完成状态，并给出"继续安装 / 重新安装 / 清理"的选择。
3. WHEN 服务已安装但启动失败 THEN System SHALL 区分"包没装好"和"装好了但起不来"，分别给出不同的处理建议。
4. WHEN 网络请求失败 THEN System SHALL 对 Node 下载和 npm 安装做有限次重试，并在国内网络下自动回退到镜像源。
5. WHEN 向导写配置 THEN System SHALL 保证配置写入是原子的，进程在写入过程中被杀不得产生损坏的配置文件。

### 非功能需求 3：可维护性

1. WHEN 需要调整安装逻辑 THEN System SHALL 只需要改统一安装器一处，桌面端和 `install.sh` 同时生效。
2. WHEN 新增一个平台的自启方式 THEN System SHALL 只需在安装器里增加一个平台分支，不需要改桌面端界面代码。
3. WHEN 排查安装问题 THEN System SHALL 能从安装器输出的结构化进度日志里还原每一步的命令和结果。
4. WHEN 新增界面文案 THEN System SHALL 走统一 i18n 字典，不得在组件里硬编码显示文字。

### 非功能需求 4：安全

1. WHEN 安装服务 THEN System SHALL 不请求管理员权限，不使用 sudo，全部装在用户目录下。
2. WHEN 下载 Node 运行时和桌面安装包 THEN System SHALL 校验官方提供的哈希值，校验不通过不得使用。
3. WHEN 写入自启配置 THEN System SHALL 只写用户级自启项，不得写入系统级目录。
4. WHEN 展示安装命令与路径 THEN System SHALL 不在界面或日志里输出任何凭据。

## 成功定义

- 一台干净电脑（没有装过 Node、没有装过 CodingNS）上，从下载桌面客户端到成功登录工作台，全程不需要打开终端。
- 同一个安装器产出的服务，在 macOS 和 Windows 上端口、数据目录、自启行为一致。
- `install.sh` 全流程仍然可用，并且在 Windows 上补上开机自启。
- 已有 Host 的老用户升级桌面端后，不会被向导打断。
- 向导相关界面文案全部来自 i18n 字典，中英文都可用。
