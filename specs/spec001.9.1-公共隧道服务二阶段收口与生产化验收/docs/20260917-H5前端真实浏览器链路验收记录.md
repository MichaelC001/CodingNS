# H5 前端真实浏览器链路验收记录

日期：2026-09-17

## 这份记录回答什么

一句话：**H5 前端在真实浏览器里到底能不能连上 Host。**

之前所有 WebRTC 联调都是在一个 Node 脚本里跑的，那里把 `RTCPeerConnection`
换成了 werift（一个 Node 里的第三方实现）。也就是说，浏览器用户真正会用到的那条路，
一次都没跑过。

这份记录补的就是这一层，并且**查出一个只在浏览器里出现、Node 侧测不出来的 bug**。

## 怎么验的

不另写模拟，让真实浏览器加载**前端真实源码**：

```text
真实 Edge 浏览器（vite dev :4174 提供真实源码模块）
  └── ManagedWebRtcTunnelHostTransport（浏览器原生 RTCPeerConnection）
        └── 控制面换票（隔离控制面 :18093，带真实 TURN）
              └── 信令服务 :18085/signal
                    └── Host 接入子进程 webrtc-peer-process.ts
                          └── 本地业务 HTTP/WS 服务 :19532
```

用的是仓库里已有的 `playwright-core`（host 的依赖）加系统里的 Microsoft Edge 153，
没有新增依赖。

跑法：

```bash
# 前置：vite dev（apps/user-app）、隔离控制面（:18093）、信令服务（:18085）
cd apps/user-app && pnpm exec tsx scripts/relay-tunnel-webrtc-browser-e2e.mts
```

脚本：`apps/user-app/scripts/relay-tunnel-webrtc-browser-e2e.mts`

## 查出来的 bug：浏览器里「直连/经中继」永远显示不出来

**现象**：浏览器链路类型一直是 `null`，设置页那行「当前链路」显示不出来。

**根因**：`getStats()` 的返回值，三种实现给的形态不一样：

| 来源 | 形态 | `instanceof Map` | `Array.isArray` |
| --- | --- | --- | --- |
| 浏览器 | `RTCStatsReport`（maplike） | false | false |
| werift | `Map` | true | false |
| 测试假实现 | 数组 | false | true |

原来的摊平代码只认后两种：

```ts
const entries = rawStats instanceof Map
  ? Array.from(rawStats.entries())
  : Array.isArray(rawStats)
    ? rawStats.map((value, index) => [String(index), value] as const)
    : [];   // ← 浏览器掉到这里，永远是空数组
```

浏览器掉进最后的 `[]`，摊平出来是空数组 → 找不到候选对 → 链路类型永远算不出来。

**为什么 Node 侧测不出来**：Node 版联调注入的是 werift，走的是 `Map` 那条分支，
永远不会碰到这个洞。这正是补浏览器验收的价值。

**修复**：把摊平逻辑挪到 `link-info.ts` 的 `toStatsArray()`，补上 maplike 分支
（用 `forEach` 遍历），并把它和候选对解析放在一起，方便单测。
`tunnel-session.ts` 改为引用同一份实现，不再各留一份。

改动文件：

- `apps/user-app/src/network/webrtc/link-info.ts`（新增 `toStatsArray`，含 maplike 分支）
- `apps/user-app/src/network/webrtc/tunnel-session.ts`（删掉本地重复实现，改用共享函数）
- `apps/user-app/src/network/webrtc/link-info.test.ts`（新增，7 条）

## 顺带确认的两件事

1. **浏览器 DataChannel 默认投递 `arraybuffer`**，不是 `blob`。
   一度怀疑浏览器会把二进制当 Blob 投递、导致下行被静默丢掉，
   实测 Edge 153 默认就是 `arraybuffer`，`toUint8Array` 那条路是好的，**不存在这个问题**。
   这一条也写进了测试断言，将来浏览器改行为能被发现。

2. **H5 前端产物已经是纯 WebRTC 客户端**。
   新构建的 `dist/` 里：`iceServers` 9 处、`createDataChannel` 1 处、`signaling/ticket` 1 处；
   旧的 `encrypted_frame` / `x25519` / `client_hello` 全为 0。

## 边界（不要夸大）

- 这台机器上 headless 浏览器做**本机 loopback ICE** 起不来（候选是 mDNS `.local`，
  或落到虚拟网卡 `198.18.0.1`），所以本验收**强制走 TURN**，没有覆盖「浏览器直连」这一支。
  生产路径本来就经 TURN，这个边界可以接受；真要在浏览器里验直连，得换真机环境。
- 控制面、信令、Host 接入子进程、业务服务都跑在同一台机器上。
  跨公网的完整形态属于 W7 的真机验收范围。
- 本验收用的是 vite dev 提供的源码，不是线上发布的产物包。
  产物包内容已单独核验（见上），但「线上地址打开能用」还需要发布后再点一遍。
