## 第二层：TURN 链路上只有密文

这一层是本次的重点，分四步做，每一步都不能省。

### 第 1 步：公网端口可达 + 凭据被生产 coturn 接受

```bash
cd apps/codingns-proxy
CODINGNS_PROXY_TURN_URLS=turn:42.193.118.236:3478 \
CODINGNS_PROXY_TURN_SHARED_SECRET=<coturn static-auth-secret> \
node scripts/verify-turn.mjs
```

原始输出（关键片段）：

```text
=== CodingNS Connect TURN 自检 ===

① 凭据签发（和控制面同一套算法）
   username        : 1789614958:verify-turn
   TURN 地址       : turn:42.193.118.236:3478

② STUN 可达性（证明端口放行、对端在说 STUN/TURN）
   ✓ turn:42.193.118.236:3478：有响应，服务端看到的本机地址是 144.255.31.231:58834
     如果这个地址是内网地址，说明 external-ip 没配好——跨网客户端会连不上。

③ 凭据是否被 coturn 接受（自己发一次 TURN Allocate 验证）
   ✓ turn:42.193.118.236:3478：成功分配到中继地址（realm=channel.codingns.com）

=== 结论 ===
通过。TURN 配置看起来是对的。
```

退出码 `0`。

**这一步证明了什么**：端口真的开了、`external-ip` 配对了（回显的是公网映射地址而不是内网地址）、
控制面与 coturn 的共享密钥一致、两台机器时间同步（否则临时凭据一签发就过期）。

补充：`3478/tcp` 也单独测过（`nc -z 42.193.118.236 3478` → succeeded），UDP 被墙时能回退。

### 第 2 步：强制 relay，确认链路真的落在中继上

```bash

RELAY_PROOF_MARKER='CNS-PROOF-9d4e2a71 GET /api/secret-path HTTP/1.1 Host: tunnel' \
node turn-relay-check.mjs
```

原始输出（关键片段）：

```text
② 收集候选（只应看到 relay 类型）
   本端候选类型 : relay
   对端候选类型 : relay
   （只配了 TURN、没配 STUN，所以候选里出现非 relay 类型才是不正常的）

③ 建立连接并等 DataChannel 打开
   ✓ DataChannel 已打开
   发起端选中链路 : relay（relay 42.193.118.236:49193 ↔ relay 42.193.118.236:49175）
   接收端选中链路 : relay（relay 42.193.118.236:49175 ↔ relay 42.193.118.236:49193）

④ 发一条可辨认内容，确认原样穿过中继
   发送内容 : CNS-PROOF-9d4e2a71 GET /api/secret-path HTTP/1.1 Host: tunnel
   收到内容 : CNS-PROOF-9d4e2a71 GET /api/secret-path HTTP/1.1 Host: tunnel
```

退出码 `0`。选中的中继端口 `49193` / `49175` 都落在收窄后的 `49152-49200` 段内。

**这一步证明了什么**：中继链路可用、数据能完整透传。**但它证明不了中继看不到内容**，所以要往下走。

### 第 3 步：真实完整链路 + 服务器端抓包

**抓包命令（在生产服务器上，需要 root）**：

```bash
sudo tcpdump -i any -n -s0 -U -w /tmp/turn-cap.pcap 'port 3478 or udp portrange 49152-49200'
```

**同时**在本机跑真实端到端（真实客户端 transport + 真实 Host 接入子进程）：

```bash
cd apps/user-app
CONTROL_BASE_URL=http://127.0.0.1:18093 \
ADMIN_EMAIL=w2-owner@example.com \
ADMIN_PASSWORD=w2-local-password-2 \
pnpm exec tsx scripts/relay-tunnel-webrtc-client-e2e.mts
```

端到端结果 **9/9 通过**，其中关键几条：

```text
[w2-e2e] PASS 客户端通过 DataChannel 拿到真实业务响应 — status=200 body={"ok":true,"from":"local-business","path":"/api/client/runtime-config?from=w2"}
[w2-e2e] PASS 1 MB 请求体分片上传（1048576 字节） — Host 侧收到 1048576 字节
[w2-e2e] PASS 120 KB WebSocket 大消息往返（分片 + 重组） — 回显 122880 字符，一致=true
[w2-e2e] PASS W2.3 真实连接上报链路类型 — phase=connected transportKind=relay（经中继，说明强制 relay 生效）
[w2-e2e] PASS W2.2 指纹被换掉时拒绝连接真实 Host
[w2-e2e] 结果：9/9 通过
```

**为什么这一步值钱**：抓包窗口里跑的不是构造出来的字节，而是真实业务——
`GET /api/client/runtime-config`、`POST /api/client/upload` 的 1 MB 请求体、120 KB 的 WebSocket 消息。
搜的就是这些真实内容。

**抓包判定**（`9166` 个包，按网络跳拆分）：

```text
【① 跨网 eth0（本机 ↔ 生产 TURN，3478）】
   包数 / 载荷字节 : 6120 / 4,535,648
   业务明文命中     : 0 次  ← 通过
   DTLS 记录        : {'Handshake': 26, 'ApplicationData': 6040, 'ChangeCipherSpec': 4}

【② 服务器本地 lo（TURN 中继端口互转）】
   包数 / 载荷字节 : 3046 / 2,254,360
   业务明文命中     : 0 次  ← 通过
   DTLS 记录        : {'Handshake': 13, 'ApplicationData': 3020, 'ChangeCipherSpec': 2}

=== 判定结果：所有中继/信令链路上业务明文命中合计 0 次 ===
```

搜索的明文特征（**全部 0 次命中**）：

| 搜索内容 | 含义 | 命中 |
| --- | --- | --- |
| `runtime-config` | 真实 HTTP 请求路径 | 0 |
| `/api/client/upload` | 真实 HTTP 上传路径 | 0 |
| `local-business` | 真实业务响应体 | 0 |
| `GET ` / `POST ` | HTTP 方法行 | 0 |
| `HTTP/1.1` | HTTP 版本行 | 0 |
| `/api/` | API 路径片段 | 0 |

跨网跳 `6040` 条 ApplicationData + `26` 条 Handshake，不是「什么都没抓到」。
`0 命中` 如果建立在空抓包上是没有意义的，这次不是。

**判定：通过。**

### 第 4 步：coturn 侧旁证

生产 coturn 服务状态 `active`，配置未做任何改动（这次验收全程没碰生产 coturn 配置，
只是从外面用它）。中继端口段收窄为 `49152-49200` 的配置在抓包里得到印证：
选中的中继端口 `49175` / `49193` 都在这段内。

### 这一层必须写清的边界

跟上次一样，这次的两个 WebRTC peer **都在本机**（客户端和 Host 接入子进程都在我的机器上）。
所以：

- **`client ↔ TURN` 那一跳是真跨公网的**（我的机器 → 腾讯云服务器），
  这一跳上抓到了 6120 个包、4.5 MB 载荷，**只有 DTLS 密文，没有业务明文**。
  这正是「ISP / 中间人能不能看到内容」所关心的那一跳。
- **`peer ↔ TURN` 那一跳落在服务器本地**（抓包里的 `lo`，`49175 ↔ 49193` 互转）。

要跑通「两个公网端点 + 生产 coturn」的完整形态，需要另一台公网机器上跑着 Host，
这属于 `W7` 真实网络验收的范围。**这次的结果不能冒充那一条。**

不过要说明的是：中继本身不看内容这件事，跟两端在不在同一台机器无关——
TURN 只做 UDP 转发，它连 DTLS 密钥都拿不到。这次抓包证明的是这个。

```sql
FROM information_schema.columns
WHERE table_schema = 'public'
  AND (column_name ILIKE '%body%' OR column_name ILIKE '%content%'
    OR column_name ILIKE '%payload%' OR column_name ILIKE '%message%'
    OR column_name ILIKE '%request%' OR column_name ILIKE '%response%');
```

| 层 | 检查什么 | 结果 |

## 这次没做到的（不许含糊）

1. **没有两个公网端点**：两个 WebRTC peer 都在本机，`peer ↔ TURN` 那一跳落在服务器本地 `lo`。
   完整的双公网端点形态留给 `W7`。
2. **没有测 TURN 用量回传**：coturn 没接 SQL 用量，日志也没开 allocation 明细。
   固定订阅模式下用量只做风控参考，这一条本来就不在 `W3.2` / `W4.2` 的验收范围里。
3. **按账号粒度的 TURN 开关仍未做**：目前只有全局开关，等 `W5` 订阅模型落地后一起补
   （这条一直挂在 `W3.2` 的备注里，这次没有变化）。

## 复跑方法

```bash
# 前置：一个隔离控制面（TURN 指向生产 coturn，强制 relay）
cd apps/codingns-proxy/apps/control-api
CODINGNS_PROXY_CONTROL_PORT=18093 \
CODINGNS_PROXY_CONTROL_DATABASE_URL=file:///tmp/codingns-w32-prod-turn.json \
CODINGNS_PROXY_INTERNAL_RELAY_API_KEY=codingns-local-relay-key \
CODINGNS_PROXY_BOOTSTRAP_ADMIN_EMAIL=w2-owner@example.com \
CODINGNS_PROXY_BOOTSTRAP_ADMIN_INITIAL_PASSWORD=w2-local-password-2 \
CODINGNS_PROXY_SIGNALING_PUBLIC_BASE_URL=http://127.0.0.1:18085 \
CODINGNS_PROXY_TURN_URLS=turn:42.193.118.236:3478 \
CODINGNS_PROXY_TURN_SHARED_SECRET=<coturn static-auth-secret> \
CODINGNS_PROXY_FORCE_TURN_BY_DEFAULT=true \
pnpm exec tsx src/main.ts

# 另开一个终端起信令服务（18085），然后：
#   服务器上起 tcpdump
#   本机跑 apps/user-app/scripts/relay-tunnel-webrtc-client-e2e.mts
# 详见本文件「第二层 第 3 步」的命令块
```

注意：隔离控制面首次启动的账号带 `mustChangePassword=true`，端到端脚本不会自己改密码，
需要先把状态文件里该账号的 `mustChangePassword` 置成 `false`（或者先手工改一次密码），
否则绑定接口会返回 `403 PASSWORD_CHANGE_REQUIRED`。
