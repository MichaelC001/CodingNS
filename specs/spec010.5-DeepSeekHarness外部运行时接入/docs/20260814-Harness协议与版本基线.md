# Harness 协议与版本基线

## 版本和协议基线

- 上游仓库：`https://github.com/deepseek-ai/deepseek-harness`
- 当前已验证应用版本：`0.1.1-rc.2`
- 校验提交：`b150a551b8d465e31e418e1b2eaf5e79bbb7d28e`
- 旧版无握手回退版本：`0.1.0-rc.5`
- 当前协议版本：`1`
- 运行前提：Node.js 22；Harness 仍是 Developer Preview，升级前必须先跑协议集成测试，再修改下方能力矩阵。

CodingNS 不合并 Harness 源码，也不直接引用它的 TypeScript 类型。Host 只通过本机 HTTP/WebSocket 调用协议。新版本是否可用由握手返回的协议版本和能力集合决定，应用版本只保留用于诊断；只有旧版没有握手字段时，才使用已验证的应用版本回退。

## 握手返回值

`host.describe` 成功后应返回以下字段（旧版字段可以继续存在）：

```json
{
  "version": "0.1.1-rc.2",
  "protocolVersion": "1",
  "capabilities": [
    "host.describe",
    "session.list",
    "session.history",
    "workspace.create",
    "session.create",
    "session.prompt",
    "session.cancel",
    "events.mux",
    "events.host"
  ]
}
```

`version` 是应用版本，不参与新协议的精确比较。`protocolVersion` 决定字段语义，`capabilities` 决定每个 RPC 是否可以调用。也接受上游把这三个字段放在 `handshake` 或 `protocol` 对象中。

## 兼容矩阵

| 场景 | Provider 状态 | 允许的操作 |
| --- | --- | --- |
| 协议 `1` 且具备必需能力 | `ready` | 按能力集合开放读写 |
| 协议 `1` 但缺少部分必需能力 | `degraded` | 只开放握手声明的能力，缺失能力返回 `HARNESS_CAPABILITY_UNSUPPORTED` |
| 未知协议，或握手缺少协议/能力集合 | `read-only` | 仅 `host.describe`、会话/工作区/模型/历史读取和事件订阅 |
| 没有握手字段且应用版本为 `0.1.1-rc.2` 或 `0.1.0-rc.5` | `ready` | 使用旧版已验证完整矩阵 |
| 没有握手字段且应用版本未知 | `read-only` | 仅安全读取，不让 Provider 从目录消失 |

写操作在 API client 发出 HTTP 请求前拦截，不能依赖 Harness 返回“未知方法”来判断兼容性。

## 启动约束

默认命令：

```text
dsh web --host 127.0.0.1 --port <动态端口>
```

默认绑定 `127.0.0.1`。`CODINGNS_DEEPSEEK_HARNESS_HOST` 只接受 `127.0.0.1` 或 `0.0.0.0`；后者必须由用户显式配置，并会把 sidecar 暴露到所有本机网络接口，部署时应由防火墙和访问网络控制。可用 `CODINGNS_DEEPSEEK_HARNESS_COMMAND` 覆盖可执行文件路径。`dsh --version` 只记录应用版本和兼容诊断，不再单独决定是否启动；真正的兼容判断在 `host.describe` 握手完成后执行。

## RPC 约定

普通调用为 `POST /api/<method>`：

```json
{
  "type": "client-request",
  "rpcId": "uuid",
  "method": "session.create",
  "payload": { "cwd": "由 Host 校验后的工作区路径" }
}
```

响应必须是同一 `rpcId` 的 `server-response`。HTTP 错误、信封错误与 `result.ok=false` 分别转换为 transport、protocol、business 三类错误。

对 approval/question 的回复必须 `POST /api/respond`，使用原始 `rpcId`：

```json
{
  "type": "client-response",
  "rpcId": "原始 server-request 的 rpcId",
  "result": { "ok": true, "value": {} }
}
```

## 下行事件

- `GET /api/events.mux`：`session/event`、tool、approval、question、queue。
- `GET /api/events.host`：会话运行状态和 Agent 错误。

socket 只做下行推送，不能发送业务命令。`events.mux.since` 在当前兼容版本没有可依赖的恢复实现，连接中断后必须先调用 `session.history` 补齐，再重建 mux/host 订阅。

## 测试夹具

`apps/host/tests/fixtures/deepseek-harness-fake-server.ts` 不读取真实模型密钥、用户主目录或工作区。它覆盖正常结果、业务错误、错配 rpcId、未知方法、mux/host 推送和连接关闭。

## 升级顺序

1. 先在 fake server 中加入新 Harness 的 `host.describe` 握手响应。
2. 运行 `deepseek-harness-sidecar-manager.test.ts`、`deepseek-harness-provider.test.ts` 和 core Provider 测试，确认读写能力、未知协议只读和旧版回退都通过。
3. 只有协议集成测试通过后，才在 `packages/session-sync-core/src/providers/deepseek-harness.ts` 更新协议版本或能力矩阵。
4. 不把真实模型调用成功、凭据有效或模型列表内容变化当作协议兼容测试结论。
