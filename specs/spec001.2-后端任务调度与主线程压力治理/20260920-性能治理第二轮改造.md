# 性能治理第二轮改造

日期：2026-09-20

这份记录补充 `spec001.2`，处理第一轮完成后仍然存在的四类真实问题：进程诊断不够可信、provider 历史缓存没有统一预算、SQLite 写队列没有硬上限，以及 `/readyz` 仍然会同步读 SQLite。

## 任务一：进程统计和诊断可信度

- 这一步做什么：把 3009 监听树、树外 CodingNS/Codex/Desktop、task-helper、app-server、relay/webrtc/ACP 等进程统一成有界、可解释的快照。
- 完成后能看到什么：每个进程有 CPU、RSS、状态、可执行文件摘要、启动/采样时间和 stale 标记；`rootPresent` 能区分存在、已消失和无法确认，并给出判断依据。
- 依赖什么：现有 `HostProcessInventoryService` 和进程表读取器。
- 主要改哪些文件：`apps/host/src/modules/system/host-process-inventory-service.ts` 及对应测试。
- 明确不做什么：不启动常驻扫描，不降低 768 MiB 高水位，不杀进程，不写数据库。
- 如何验证：覆盖两次 CPU 采样、root 消失、权限不足、摘要失败、树外 Codex/Desktop、stale 快照和数量/命令行边界。
- 当前状态：已完成（25 项进程统计测试通过）。

## 任务二：Provider 历史缓存预算

- 这一步做什么：提供统一的加权 LRU，把 provider、workspace、session 的历史缓存限制在条目数和真实字节预算内。
- 完成后能看到什么：缓存命中、未命中、淘汰、拒绝和当前字节数可观测；超大内容旁路，不会因为一次读取把 helper 内存撑大。
- 依赖什么：现有各 provider 的惰性历史读取和增量读取逻辑。
- 主要改哪些文件：`packages/session-sync-core/src/providers/*`、通用缓存模块及测试。
- 明确不做什么：不全量预加载历史，不改变 provider 协议，不通过频繁重启 helper 解决内存问题。
- 如何验证：覆盖 UTF-8 字节数、全局预算、多 provider 并发、高水位淘汰、失败不缓存和并发一致性。
- 当前状态：已完成（缓存测试 5/5、session-sync-core 构建通过）。

## 任务三：有界 SQLite 命令队列

- 这一步做什么：把 SQLite 写入排队改成有 pending 数量和字节上限的类型化命令队列，并定义不同命令的超限策略。
- 完成后能看到什么：队列满时返回明确 backpressure；`latest_wins`、`append_batch`、`critical`、`best_effort` 的行为和统计都能被测试验证。
- 依赖什么：现有 better-sqlite3 封装和写入重试逻辑。
- 主要改哪些文件：`apps/host/src/storage/sqlite/write-queue.ts`、`write-serializer.ts` 及测试。
- 明确不做什么：不使用 `node:sqlite`，不使用 `Atomics.wait`，不先修改 `auth_users` 索引。
- 如何验证：覆盖队列满、pending bytes、锁竞争、事务失败恢复、关闭 drain 和拒绝新任务。
- 当前状态：已完成（SQLite 队列/诊断定向测试通过）。

## 任务四：SQLite Writer 与 readiness

- 这一步做什么：建立独立 writer 的 Host/Helper 协议，让 `/readyz` 只读内存快照，不再同步执行 SQL。
- 完成后能看到什么：readiness 能显示 writer 心跳、最近事务、锁等待、错误、pending 数量/字节、过期和降级状态；短暂锁竞争不会直接重启 Host。
- 依赖什么：有界写队列的稳定接口。
- 主要改哪些文件：`apps/host/src/modules/health/health-service.ts`、supervisor 入口、writer 协议和测试。
- 明确不做什么：不把所有历史同步写路径一次性重写；暂时无法迁移的路径必须在代码和文档中标明边界。
- 如何验证：锁竞争时 `/readyz` 仍快速返回，writer 崩溃/重启/retiring/关闭时行为明确，Host 请求路径无同步 SQLite。
- 当前状态：IN_REVIEW。生产启动链路已接入独立 `sqlite-writer-process`，Host 通过 `sqlite-writer-client` 发送类型化命令并读取内存 heartbeat；会话状态、状态快照、会话索引和工作区导航状态已进入 writer/共享有界队列；writer 异常退出后最多自动重启 3 次并重建 readiness 桥。认证、工作区创建/删除、部分索引类同步 CRUD 仍需按返回值和事务语义逐项迁移，不能用丢弃返回值的方式强行改成异步。

## 本轮补充：非阻塞兼容边界

- `write-serializer.ts` 不再使用 `Atomics.wait`。旧同步调用只做立即重试，带退避的写入必须走 `SqliteWriteQueue` 或独立 writer。
- Provider 的订阅计数、watcher/fallback 触发、每秒 delta read 和所有已接入 provider 的缓存命中/淘汰/字节数已接入运行时观测快照的 `provider` 字段。

## 关键写路径迁移进度

本阶段按接口语义逐步迁移，不把所有 repository 方法机械改成异步：

- 已完成：认证用户创建、编辑、删除、停用；停用操作将用户、token、设备会话更新放在同一 Writer transaction 中。工作区导入、克隆登记、移除也会等待 Writer 的 critical ack。
- 已完成：会话状态、状态快照、会话索引、工作区导航状态使用 Writer 或共享有界队列。
- 待处理：用户停用时的 token/设备会话级联事务、工作区级联删除、需要读后写强一致的业务 CRUD。
- 明确边界：同步兼容方法只供启动迁移、后台清理和 `:memory:` 测试使用，普通 HTTP 写路径不再调用这些方法。
