# 设计文档 - SQLite 写入串行化与会话终态一致性

状态：Draft

## 1. 概述

### 1.1 目标

- 在 Host 进程内建立一个共享的 SQLite 写入队列，统一处理高频运行时和扫描写入。
- 把锁重试、耗时观测和失败释放放进一个小而明确的组件。
- 让终端 writer 的文件追加与索引提交保持可重试、可幂等。
- 将不存在活动运行的中断请求收敛为幂等终态操作。

### 1.2 覆盖需求

- `requirements.md` 需求 1、需求 2、需求 3。

### 1.3 技术约束

- 后端：Node.js 22、TypeScript、Fastify。
- 数据存储：现有 `better-sqlite3` 和 WAL 模式。
- 并发模型：Host 进程内异步队列；终端 writer 仍是独立进程。
- 不使用 `node:sqlite`，不把正文写入 SQLite。

## 2. 架构

### 2.1 系统结构

`createDatabaseClient()` 创建数据库连接时同时创建 `SqliteWriteQueue`。需要高频写入的服务持有同一个队列实例：

1. 运行时事件先完成 provider 事件解析，再把一组相关索引/状态写入排队。
2. 工作区发现按现有批次事务执行，每个批次通过同一队列提交，批次之间让出事件循环。
3. WebSocket 订阅只在需要保存快照时排队写入，不在广播回调中直接抢写锁。
4. 终端 writer 先追加文件，再用请求 ID 作为分段 ID 提交 SQLite；提交失败只重试数据库提交。

### 2.2 模块职责

| 模块 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- |
| `SqliteWriteQueue` | FIFO 执行 Host 写操作、有限退避、记录耗时 | scope、同步/异步写函数 | 写入结果或原始错误 |
| `SessionLiveRuntimeService` | 让运行时事件的高频状态写入复用共享队列 | runtime event | 持久化完成 Promise |
| `SessionHistoryService` | 让发现批次和订阅快照使用短事务与队列 | discovery batch、snapshot | 索引/快照 |
| `terminal-log-writer-process` | 文件追加和幂等日志索引提交 | request id、分段范围 | writer result |

### 2.3 关键流程

#### 2.3.1 Host 写入流程

1. 调用方把带 scope 的写函数交给共享队列。
2. 队列等待前一个写函数结束，然后执行一次短事务。
3. 遇到 busy 错误按固定退避重试；每次重试不重复生成外部副作用。
4. 成功或最终失败都释放队列尾部，让下一项继续。

#### 2.3.2 终端日志流程

1. writer 在 SQLite 中准备/获取活动文件，事务结束后追加本地文件。
2. 用稳定的请求 ID 作为 segment ID 提交分段和文件尾部。
3. 提交因锁失败时重复同一个 segment ID；重复插入被忽略，文件尾部只取最大值。
4. 返回成功前同时确认文件追加和索引提交都完成。

## 3. 组件和接口

### 3.1 核心组件

- `SqliteWriteQueue`：唯一的 Host 进程内写入排队入口。
- `runSqliteWriteWithRetry`：有限 busy 重试和观测的共享实现。
- `TerminalLogWriter` 提交事务：以 request ID 保证分段幂等。
- `interruptSession` 终态分支：把活动运行不存在视为已结束。

### 3.2 数据结构

#### 3.2.1 写入任务

| 字段 | 类型 | 必填 | 说明 | 约束 |
| --- | --- | --- | --- | --- |
| `scope` | `string` | 是 | 观测名称 | 不含用户正文 |
| `run` | `() => T \| Promise<T>` | 是 | 短写操作 | 不得包含文件追加或网络调用 |
| `maxRetries` | `number` | 否 | busy 重试上限 | 默认有限值 |

#### 3.2.2 终端日志提交

| 字段 | 类型 | 必填 | 说明 | 约束 |
| --- | --- | --- | --- | --- |
| `requestId` | `string` | 是 | 一次批次的稳定 ID | 同一提交重试保持不变 |
| `fileId` | `string` | 是 | 活动日志文件 ID | 必须存在 |
| `startSeq/endSeq` | `number` | 是 | 分段序号范围 | `endSeq >= startSeq` |
| `startOffset/endOffset` | `number` | 是 | 文件偏移 | 不允许倒退 |

### 3.3 接口契约

#### 3.3.1 `SqliteWriteQueue.enqueue`

- 类型：Function
- 输入：`scope`、写函数和可选重试配置。
- 输出：写函数返回值的 Promise。
- 校验：写函数必须是短事务；队列关闭后拒绝新任务。
- 错误：保留原始 SQLite 错误；重试耗尽后只失败当前任务。

#### 3.3.2 终端 writer persist

- 类型：进程 stdin/stdout RPC。
- 输入：现有 `persist` 请求，`id` 同时作为幂等 segment ID。
- 输出：现有 `{ type: "result", id, ok }`。
- 校验：请求范围和内容必须有效。
- 错误：文件追加失败或索引最终失败均返回 `ok: false`。

## 4. 数据与状态模型

### 4.1 数据关系

一个终端批次对应一个日志文件分段。文件正文是事实来源，SQLite 只保存文件 ID、序号和偏移；请求 ID 绑定到该分段，重试只能更新同一分段。

### 4.2 状态流转

| 状态 | 含义 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| `queued` | 等待 Host 写入队列 | 调用 `enqueue` | 开始执行 |
| `running` | 正在执行短事务 | 获得队列 | 成功或失败 |
| `retrying` | 遇到临时 busy | 当前尝试失败 | 重试或耗尽 |
| `committed` | 数据已一致落库 | 事务成功 | 只读 |

## 5. 错误处理

### 5.1 错误类型

- `SQLITE_BUSY`：临时锁竞争，进入有限退避。
- `TERMINAL_LOG_COMMIT_FAILED`：文件已追加但索引无法最终提交，返回失败并保留可恢复信息。
- `ACTIVE_RUN_NOT_FOUND`：活动运行已结束，按幂等终态处理。

### 5.2 处理策略

1. SQLite busy：队列内重试，记录等待时间，耗尽后失败当前任务。
2. 终端提交失败：不再追加文件；同一 request ID 可再次提交。
3. 中断竞态：先读取运行快照；无活动运行时同步终态并返回成功。
4. 所有写入失败都必须释放队列，不吞掉非 busy 错误。

## 6. 正确性属性

### 6.1 属性 1：写入顺序

*对于任何* 同一个 Host 写入队列中的任务，后入队任务不会在前一任务完成前执行。

**验证需求：** 需求 1。

### 6.2 属性 2：终端日志幂等

*对于任何* 同一个 request ID 的重复提交，`terminal_log_segments` 最多只有一条对应分段，文件尾部不会倒退。

**验证需求：** 需求 2。

### 6.3 属性 3：终态单调

*对于任何* 已进入终态的会话，后续中断或延迟事件不能把状态写回活动态。

**验证需求：** 需求 3。

## 8. 风险与待确认项

### 8.1 风险

- 只把高频链路接入队列，低频管理写入仍可能与终端 writer 竞争；需要通过日志确认剩余热点。
- 终端 writer 跨进程仍可能遇到外部连接持锁，因此必须保留有限重试而不是假设永不冲突。

### 8.2 待确认项

- 本轮不迁移终端日志索引到独立数据库；若后续仍有跨进程锁等待，再单独立项拆库。
