# spec001.9-公共隧道服务接入与端到端加密远程访问

状态：Draft（2026-09-16 按 WebRTC 承载层改版）

## 当前定位

这是 `spec001` 下的子 Spec，也是 `spec001.4-Tailscale接入与实例级远程访问` 之后的下一步。

它解决一件事：
把「用户只能在局域网或自建网络里访问 Host」升级成「通过 CodingNS 自己托管的公共隧道服务访问 Host」，
并且让传输是端到端加密的——**公共中继只能看到密文字节和连接元数据，看不到业务内容**。

**2026-09-16 改版要点**：承载层从「WSS 盲中继 + 自研端到端加密」换成 **WebRTC DataChannel**。

- 端到端加密改由 WebRTC 的 DTLS 原生提供，不再自研握手和加密帧
- 优先 P2P 直连（数据不过服务器），NAT 打洞失败才回落 TURN
- 计费从「按流量」改成「固定订阅」——P2P 打通后网络层无法计量

改版依据见 [docs/20260916-WebRTC承载层验证结论.md](./docs/20260916-WebRTC承载层验证结论.md)。

## 计划覆盖

- 实例级公共隧道配置模型、绑定状态和最近状态快照
- Host 侧 WebRTC 接入层（werift，独立进程）、信令连接、自动重连和启动恢复
- 客户端 / H5 侧的 DataChannel 建立、DTLS 指纹校验和业务转发
- 公共服务控制面、信令服务和 TURN 的仓库边界
- Host 绑定、DTLS 指纹登记与展示
- P2P 优先、TURN 兜底，以及当前链路类型的展示
- 固定订阅的购买、续期和状态展示
- 用量统计（风控口径，不再作为计费依据）
- 设置页里的公共隧道入口、绑定、启停、状态展示
- 与现有本地直连、局域网直连、Tailscale 远程访问并存的规则

## 必须记住的四条边界

1. **端到端加密由 DTLS 提供，不是自研的**。信令服务器和 TURN 都拿不到密钥，这是协议保证的。
2. **对端身份靠 DTLS 指纹校验**。指纹从控制面独立取回，与 SDP 里的比对，不一致必须拒绝，不允许降级。
3. **P2P 直连会暴露双方公网 IP**。自己连自己的设备没问题，一旦涉及分享给他人必须重新评估。
4. **上行吞吐只有 3–6 MB/s**（实测）。下行 21–31 MB/s 够用，上行是不是够用要按业务判断。

## 本阶段明确不做

- 在本仓库里实现公共隧道站点、支付后台和信令 / TURN 服务代码
- 把「公共隧道服务」抽象成支持无限多供应商的通用网络平台
- 用公共隧道服务替代现有 CodingNS 登录体系
- 假装「用户自有域名直接出 H5 页面」还能同时保证中继永远看不到内容
- 第一阶段就做团队订阅、共享额度、多租户企业后台
- 把访问权限分享给第三方（涉及 P2P 暴露 IP，需要单独评估）

## 仓库边界

- **本仓库**：只放 `Spec`、Host 侧 WebRTC 接入层、客户端 / H5 接入层、设置页入口
