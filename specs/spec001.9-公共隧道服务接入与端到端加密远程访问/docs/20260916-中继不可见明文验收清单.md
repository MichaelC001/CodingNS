# 「中继不可见明文」验收清单

日期：2026-09-16
对应任务：`tasks.md` W4.2
依据：`design.md` 第 5 节、`docs/20260916-WebRTC承载层验证结论.md`、`docs/20260916-TURN部署与接入说明.md`

## 这份文档回答什么

「中继不可见明文」这句话不能靠感觉。这份文档把它拆成**三层可以真正执行、可以判定通过或失败**的检查：

| 层 | 检查什么 | 现在能不能跑 |
| --- | --- | --- |
| 第一层：信令 | 信令服务器能不能被拿来承载业务数据 | **可以，已自动化** |
| 第二层：TURN | 中继链路上跑的是不是密文 | 需要 TURN 部署完成（W3.2） |
| 第三层：日志与数据库 | 服务端落盘的东西里有没有业务内容 | 部分可以（代码走查 + 本地栈） |

**判定标准只有一条：任一层里能找到可读的业务内容，就算失败。**
「看起来是乱码」「大概没问题」都不算通过。

## 第一层：信令服务器不承载业务数据

### 为什么这一层重要

信令服务器是我们自己的服务，它**故意**能看到 SDP 和 ICE 候选。
所以风险不是「它偷看」，而是「它被当成一条业务通道用了」——
一旦有人能把业务字节塞进信令消息，中继就又变成能看到内容的中继了。

### 怎么验证

**自动化（已落地，随时可重跑）：**

```bash
cd apps/codingns-proxy
pnpm --filter @codingns-proxy/relay-signaling test
```

其中这条用例就是本层的门禁：

> `信令链路不承载业务数据：业务形状的消息一律拒绝且不转发`

它做的事：Host 和客户端都连上之后，客户端发一条长得像业务请求的消息
（`type: "http.request"`，带 `path` / `headers` / `body`），然后断言两件事：

1. 发送方收到 `MESSAGE_INVALID` 错误
2. **Host 侧一条消息都没多收到**（比对消息条数）

**通过的判据**：测试全绿。

**失败的判据**：Host 侧多收到了任何一条消息，说明信令通道能被当业务通道用。

### 代码层面的边界（不用工具，肉眼看）

- 信令服务器接受的客户端消息只有四种：`ping` / `offer` / `answer` / `candidate`
- 它**不解析 SDP 内容**，只做转发（内容是否合法由两端自己的 WebRTC 栈判断）
- 它拿不到 DTLS 密钥——密钥是两端协商出来的，从不经过信令

### 一个必须知道的边界

SDP 是一个文本字段，理论上有人可以往里面塞额外字节，让信令服务器替它搬运。
**这不影响「中继不可见明文」**——因为 DTLS 密钥不在 SDP 里，塞进去的字节中继依然读不懂。
但它确实意味着信令通道不应该被当成可靠的数据通道用（带宽和稳定性都不合适）。
这条留作已知边界记录，本轮不做额外限制。

## 第二层：TURN 链路上只有密文

### 前置

TURN 已经按 `docs/20260916-TURN部署与接入说明.md` 部署好，并且已经跑过：

```bash
cd apps/codingns-proxy
pnpm verify:turn
```

自检通过（`exit 0`）只说明「凭据能签发、端口通、密钥对得上」，
**不能替代本层的抓包验收**。

### 怎么验证

**第一步：强制走 TURN，确保流量真的经过中继。**

```bash
CODINGNS_PROXY_FORCE_TURN_BY_DEFAULT=true
```

这一步不能省。TURN 配错了经常表现为「平时也能连上」——因为直连成功了，TURN 根本没被用到。
只有强制 relay 才能把它暴露出来。

**第二步：确认链路真的落在 relay 上。**

连接建立后读选中的候选对：`local.type === "relay" || remote.type === "relay"` 才算真的走了 TURN。
`apps/host/scripts/relay-tunnel-webrtc-e2e.mjs` 会把链路类型打出来（`kind: relay` / `p2p`），
**必须是 `relay`**，否则后面抓到的包根本不代表中继链路上的流量。

**第三步：在 TURN 服务器上抓包。**

```bash
sudo tcpdump -i any -n -s0 -A port 3478 | head -200
```

同时从客户端跑一段**内容可辨认**的业务操作，比如打开一个会返回明文 JSON 的接口，
或者在会话里发一条内容特殊的消息。

**通过的判据**（三条都要满足）：

1. 抓到的包是 DTLS 记录（能看到 TLS/DTLS 握手记录类型，而不是 HTTP 请求行）
2. **看不到 HTTP 方法名、请求路径、请求头**（搜不到 `GET `、`POST `、`/api/`、`host:`）
3. **搜不到刚才那条特意准备的可辨认内容**（这是关键——用一个自己造的、不可能碰巧出现的字符串去搜）

**失败的判据**：上面第 2 或第 3 条能搜到，说明中继承担了 TLS 终结，方案前提被破坏。

**记录要求**：抓包命令、搜索用的字符串、命中的（或没命中的）原始输出，都要贴进验收记录。
不接受「我看了，是乱码」这种结论。

#### 关于抓包权限（2026-09-16 记）

`tcpdump` 抓包需要 root，在 macOS 上 `lo0` 也不例外
（`tcpdump: lo0: You don't have permission to capture on that device`）。
**开发机上通常拿不到这个权限，所以第二层的抓包验收要在目标服务器上做，不要在本地糊弄过去。**

如果确实需要在拿不到 root 的环境里留下证据，只能做到「链路类型是 relay」这一步（上面的第二步），
**这只能证明流量经过了中继，证明不了中继看不到内容**。
两者不能互相替代，验收记录里要写清楚实际做到哪一步。

## 第三层：日志与数据库里没有业务内容

### 信令服务日志

```bash
# 本地栈
tail -f apps/codingns-proxy/.local/run/logs/relay-signaling.log

# 正式环境
pm2 logs <relay-signaling 应用名>
```

**通过判据**：日志里只有绑定、角色、会话 id、时间、连接数这类元数据；
不应出现请求路径、请求头、请求体、响应体。

信令的调试日志默认关闭（`CODINGNS_PROXY_SIGNALING_DEBUG_LOGS=false`）。
**排障时临时打开可以，但排障完必须关掉**，并把它当成一次「临时放宽」记录下来。

### 控制面数据库

这一层的思路不是「搜一遍看有没有」，而是**先确认表里根本没有能放业务内容的列**，
再确认没有别的表偷偷存了内容。

**第一步：看用量相关的表到底有哪些列。**

```sql
SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE table_name IN ('relay_usage_events', 'relay_usage_daily_summaries')
ORDER BY table_name, ordinal_position;
```

**通过判据**：这两张表的列只有三类东西——标识（`session_id` / `account_id` / `binding_id`）、
字节数（`upstream_bytes` / `downstream_bytes`）、时间戳。**没有任何 text / json / blob 类型的业务内容列。**

这两张表的完整列（2026-09-16 核对 `database-migrations.ts`）：

| 表 | 列 |
| --- | --- |
| `relay_usage_events` | `usage_id`、`session_id`、`account_id`、`binding_id`、`upstream_bytes`、`downstream_bytes`、`observed_at`、`processed_at` |
| `relay_usage_daily_summaries` | `account_id`、`binding_id`、`summary_date`、`upstream_bytes`、`downstream_bytes`、`event_count`、`session_count`、`first_observed_at`、`last_observed_at`、`aggregated_at` |

**这个检查比「搜关键词」强**：搜关键词只能证明「这次没搜到」，
而列结构能证明「这里压根没有地方可以存」。**如果哪天有人给这两张表加了内容列，
这个检查会立刻失败**——这正是它该有的作用。

**第二步：确认没有别的表被顺手拿来存内容。**

```sql
SELECT table_name, column_name
FROM information_schema.columns
WHERE table_schema = 'public'
  AND data_type IN ('text', 'json', 'jsonb', 'bytea')
ORDER BY table_name, column_name;
```

逐个看过这些列，确认它们存的是配置、标识、错误信息之类的元数据，
**没有一个是「请求体 / 响应体 / 消息内容」**。

### Host 侧

Host 的接入进程**不写任何持久化**（见 `docs/20260916-Host接入进程模型.md` 第六节），
所以这一层天然没有可查的落盘内容。这一点本身也要在验收记录里写一句，
因为「没有可疑数据」和「根本没有数据」是两回事。

## 怎么留证据

W4.2 要求「有一份可重复执行的验收记录」。每次执行后追加到
`specs/spec001.9.1-公共隧道服务二阶段收口与生产化验收/docs/` 下的一份记录里，包含：

1. 执行日期与执行人
2. 三层的实际命令
3. 每层的原始输出（关键片段即可，但要能看出是通过还是失败）
4. 结论：三层是否全部通过；未通过的是哪层、卡在哪
