# TURN（coturn）部署与接入

日期：2026-09-16
对应任务：`tasks.md` W3.2
前置：`docs/20260916-信令与ICE配置下发说明.md`

## 一、为什么需要 TURN

WebRTC 优先打洞直连（P2P）。但下面这些情况打不通：

- 双方都在对称 NAT 后面
- 企业防火墙只放行 443
- 运营商做了 CGNAT

这时需要一个双方都能连上的中转。TURN 就是这个中转。

**关键前提：TURN 只转发 DTLS 密文。** 它看到的是加密后的字节流，
不知道里面是 HTTP 还是别的什么，也拿不到任何密钥。这一点是这套方案能成立的前提，
不是可选项。

## 二、为什么不自己写

自研中继（旧方案）的问题是：要自己实现端到端加密套件，三端各一份拷贝。
换成 coturn 之后，加密由 WebRTC 自带的 DTLS 承担，TURN 只做 UDP/TCP 转发，
是一个被广泛使用、专门解决这个问题的组件。

## 三、部署步骤

### 3.1 安装

```bash
sudo apt-get update
sudo apt-get install -y coturn

# 让 coturn 以服务方式常驻
sudo sed -i 's/^#TURNSERVER_ENABLED=1/TURNSERVER_ENABLED=1/' /etc/default/coturn
```

### 3.2 配置

用仓库里的模板：

```bash
sudo cp deploy/templates/coturn.conf.template /etc/turnserver.conf
```

然后替换这几个占位符：

| 占位符 | 填什么 |
| --- | --- |
| `__LISTEN_IP__` | 本机内网 IP，例如 `10.0.0.8` |
| `__EXTERNAL_IP__` | 公网 IP。**云主机在 NAT 后面时必须填**，否则 coturn 会把内网地址发给客户端，客户端连不上 |
| `__TURN_SHARED_SECRET__` | 与控制面 `CODINGNS_PROXY_TURN_SHARED_SECRET` **完全一致**的随机串 |
| `__TURN_REALM__` | 你的域名，例如 `channel.codingns.com` |

生成密钥：

```bash
openssl rand -hex 32
```

### 3.3 防火墙

需要放行：

- `3478/udp` — 主要通道
- `3478/tcp` — UDP 被墙时的回退
- `49152-65535/udp` — 中继端口范围

如果只放行 443，可以额外配 `alt-listening-port=443`，但那样要和 nginx 协调端口。

### 3.4 启动

```bash
sudo systemctl enable coturn
sudo systemctl restart coturn
sudo systemctl status coturn
```

## 四、和控制的对接

控制面不存 TURN 账号密码，用的是 coturn 的 REST API 临时凭据模式：

```text
username   = <过期时间戳>:<账号标识>
credential = base64(hmac-sha1(username, sharedSecret))
```

coturn 侧只需要 `static-auth-secret`，客户端拿到的凭据自带过期时间。
这样控制面不用为每个用户建 TURN 账号，也不用存长期密码。

控制面这边配：

```bash
CODINGNS_PROXY_TURN_URLS=turn:turn.codingns.com:3478
CODINGNS_PROXY_TURN_SHARED_SECRET=<和 coturn 一致>
CODINGNS_PROXY_TURN_CREDENTIAL_TTL_SECONDS=3600
```

**两边的密钥必须完全一致**，否则客户端拿到的凭据会被 coturn 拒绝，
表现为「ICE 一直连不上但日志里没有明显报错」。

## 五、怎么验证

### 5.1 先确认 TURN 本身活着

```bash
# 换一个临时凭据（把密钥和过期时间换成自己的）
SECRET="你的static-auth-secret"
TTL=3600
USERNAME="$(( $(date +%s) + TTL )):probe"
CREDENTIAL="$(printf '%s' "$USERNAME" | openssl dgst -binary -sha1 -hmac "$SECRET" | openssl base64)"

# 用官方工具或浏览器控制台验证
turnutils_uclient -u "$USERNAME" -w "$CREDENTIAL" -p 3478 turn.codingns.com
```

### 5.2 再验证强制走 TURN

控制面打开开关：

```bash
CODINGNS_PROXY_FORCE_TURN_BY_DEFAULT=true
```

然后让客户端连接。在浏览器 `chrome://webrtc-internals` 里看：

- 选中的候选对类型应该是 `relay`
- 不应该出现 `host` / `srflx` 被选中

**这一步必须真的做**，不能只看配置。TURN 配错了经常表现为「平时也能连上」——
因为直连成功了，TURN 根本没被用到。只有强制 relay 才能暴露问题。

### 5.3 验证中继看不到明文

在 TURN 服务器上抓包：

```bash
sudo tcpdump -i any -n port 3478 -A | head -50
```

应该只能看到 DTLS 握手和加密的应用数据，看不到 HTTP 头、看不到业务内容。

## 六、配额与限速

模板里给了保守默认值：

- `user-quota=12`：单账号并发分配数
- `total-quota=1200`：全局并发分配数
- `max-allocate-lifetime=3600`：单次分配最长 1 小时

固定订阅模式下，TURN 带宽是主要成本。按实际套餐调整这几个值，
不要一上来给很大，否则一个异常客户端就能把出口打满。

## 七、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 客户端一直连不上，日志没报错 | 两边密钥不一致 | 核对 `static-auth-secret` 和控制面配置 |
| 直连正常，跨网就连不上 | 没配 `external-ip` | 补上公网 IP |
| TURN 能连但很慢 | 只走了 TCP | 放行 `3478/udp` |
| 客户端拿到凭据被拒 | 服务器时间不同步 | 两台机器都要对时（NTP） |
| 中继端口连不上 | 防火墙没放行 `49152-65535/udp` | 放行或改 `min-port`/`max-port` |

**时间同步这条特别容易踩**：临时凭据里有过期时间戳，
如果控制面和 TURN 服务器时间差太多，凭据一签发就是过期的。

## 八、还没做的

- **按账号粒度的 TURN 开关**：目前只有全局开关 `CODINGNS_PROXY_FORCE_TURN_BY_DEFAULT`。
  等 W5 订阅模型落地后，改成按订阅状态决定是否下发 TURN。
- **TURN 用量回传**：coturn 支持把用量写进 SQL，但目前没有接。
  固定订阅模式下用量只用于风控，不是计费依据，所以优先级不高。
- **多地域 TURN 调度**：目前是单点。用户量上来后再考虑。
