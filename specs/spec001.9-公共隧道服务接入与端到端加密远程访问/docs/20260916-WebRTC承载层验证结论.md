# WebRTC 承载层验证结论

日期：2026-09-16

## 这份文档要回答什么

公共隧道的承载层能不能从「WSS + 自研端到端加密」换成「WebRTC DataChannel」。

结论全部来自 `apps/codingns-proxy/local/webrtc-datachannel-demo/` 的实测，不是查资料抄来的。
复现方式写在那个目录的 README 里。

## 一句话结论

**可行，但要接受两个硬限制。**

1. Host 侧只能用 `werift`（纯 TypeScript），另一个候选 `node-datachannel` 收数据会丢，不能用。
2. **上行吞吐只有 3–6 MB/s**，下行 21–31 MB/s。下行够用，上行是不是够用要业务上判断。

## 一、端到端加密成立，中继看不到明文

DTLS 在客户端和 Host 之间端到端协商，密钥不经过信令服务器，也不经过 TURN。

- 信令服务器全程只经手 SDP 和 ICE 候选，拿不到数据密钥
- TURN 只转发 DTLS 密文，同样看不到内容

这一条不需要我们自己写代码，是 WebRTC 协议本身提供的。

**因此现有那套自研端到端加密可以整个删掉**：

| 现有实现 | 代码量 | 处置 |
| --- | --- | --- |
| `relay-tunnel-protocol.ts`（x25519 + HKDF + AES-GCM + AAD） | 658 行 | 删除 |
| `host-proof.ts`（challenge proof 校验） | — | 删除，改校验 SDP 里的 DTLS 指纹 |
| `relay-tunnel-packets.ts` / `relay-tunnel-identity.ts` | — | 删除 |
| base64 + JSON 信封 | — | 删除，DataChannel 直接收发二进制 |

上面这套协议目前在 `apps/host`、`apps/user-app`、`apps/codingns-proxy/apps/relay-edge` 各存一份副本，
共三份，靠人工保持一致。其中 relay-edge 那份已经是没人 import 的死代码。

## 二、Host 侧实现选型：node-datachannel 出局

Host 是 Node 进程，需要自己选一个 WebRTC 实现。两个候选实测对比（同一台机器、同一时间窗口、同样脚本交替跑）：

| 指标 | node-datachannel（libdatachannel） | werift（纯 TypeScript） |
| --- | --- | --- |
| **浏览器→Host 5 MB 成功率** | **3/16（19%）** | **11/11（100%）** |
| 浏览器→Host 20 MB | 未测（5 MB 已经挂） | 通过，校验一致 |
| 上行吞吐 | 16–58 MB/s | 3–6 MB/s |
| 下行吞吐 | 46–49 MB/s | 21–31 MB/s |
| 部署形态 | N-API 预编译二进制 | 零编译 |

node-datachannel 的失败特征：数据灌入后 **ICE 状态从 completed 直接跳 failed**，底层没有 SCTP 报错，
典型表现是收到约 2 MB 后断链。收尾时还会抛 `cleanup timeout (possible deadlock)`，
这是未捕获异常，**会直接杀掉整个 Node 进程**。

三轮独立实验：

| 实验 | node-datachannel | werift |
| --- | --- | --- |
| 交替 3 轮 | 3/3 | 3/3 |
| 10 轮 / 5 轮 | **0/10** | 5/5 |
| 交替 3 轮 | **0/3** | 3/3 |

第一次的 3/3 是 node-datachannel 唯一一次全过，之后连续 13 轮全挂。同样的代码、同样的机器、
同样的数据量，成功率在 0% 和 100% 之间跳——**这种不可预测本身就是不能上生产的理由**。

上游有对应的已知缺陷：node-datachannel issue #375「Intermittent data loss」（2025-09 提交，至今 Open），
维护者的说法是同一份代码在 Chrome 和 Firefox 里正常，所以问题在 Node 侧这个实现。

**结论：Host 侧用 werift。**

## 三、吞吐实测：调优改不动上行，改的只是本地数字

三条优化路径都试过了：**分片、水位、多通道，对上行真实吞吐都没有稳定收益**。

### 3.1 量测口径先要说清楚

页面侧统计的「上传完成耗时」**不可信**——它只统计数据写进本地 SCTP 缓冲区的时间，
不是对端收到的时间。水位调大后 5 MB 几乎一次就能塞进缓冲，页面会报出 88 MB/s，
而 Host 实测只有 8 MB/s，**虚高十倍以上**。

同一个连接同一次传输的两套数字：

| 口径 | 耗时 | 吞吐 |
| --- | --- | --- |
| 页面侧「上传完成」（写入缓冲区） | 57 ms | 88.5 MB/s（假） |
| **Host 侧实测（收到首字节 → 结束）** | **612 ms** | **8.2 MB/s（真）** |

以后看吞吐只认 Host 侧打点，页面数字只能当「本地排空速度」参考。

### 3.2 方法论：单批次测试会骗人，必须交替跑

这一条比数据本身更重要，因为我自己先踩了一次。

第一轮参数矩阵是**每组连续跑 3 轮**，得到的结论是「64 KB + 4 MB 比默认快 2.7 倍」：

| 分片 | 水位 | 三轮上行 (MB/s) | 平均 |
| --- | --- | --- | --- |
| 16 KB | 1 MB | 2.9 / 3.7 / 2.6 | 3.1 |
| 64 KB | 4 MB | 9.6 / 10.9 / 4.8 | 8.4 |

但把这两个配置**交替跑各 5 轮**（消除时间漂移）之后，差异消失了：

| 配置 | 五轮上行 (MB/s) | 平均 |
| --- | --- | --- |
| 16 KB / 1 MB | 5.3 / 4.9 / 3.3 / 2.6 / 4.7 | 4.2 |
| 64 KB / 4 MB | 2.8 / 4.1 / 3.7 / 6.1 / 6.2 | 4.6 |

两组平均差 10%，而单轮波动范围是 2.6 ~ 6.2 —— **这个差异是噪声，不是参数效果**。

原因：测试机负载一直在变。连续跑同一配置时，整组数据会被同一段负载条件「染色」，
看起来像是配置带来的差异。**只有交替跑才能把时间因素抵消掉。**

### 3.3 参数矩阵：两批顺序跑给出了两个不同的「最优解」

同样四个配置、同样每组 3 轮，**顺序跑了两批**，结果互相矛盾：

| 分片 | 水位 | 第一批上行 (MB/s) | 平均 | 第二批上行 (MB/s) | 平均 |
| --- | --- | --- | --- | --- | --- |
| 16 KB | 1 MB | 2.9 / 3.7 / 2.6 | 3.1 | 4.3 / 3.4 / 5.2 | 4.3 |
| 64 KB | 1 MB | 11.3 / 7.2 / 2.5 | 7.0 | 4.3 / 6.5 / 5.0 | 5.3 |
| 16 KB | 4 MB | 4.8 / 2.7 / 4.1 | 3.9 | 3.7 / 6.3 / 5.2 | 5.1 |
| 64 KB | 4 MB | 9.6 / 10.9 / 4.8 | 8.4 | 3.2 / 6.4 / 8.9 | 6.2 |

第一批看上去「分片调到 64 KB 就快 2.7 倍」，第二批同一对比只剩 1.4 倍，交替跑（3.2 节）只有 1.1 倍——
**同一套参数，三个结论**，而且三批全部落在单轮波动区间 2.5–11.3 MB/s 之内。

下行倒是很稳：两批都是 21–31 MB/s，只有个别轮次出现离群值（1.5 / 12.8 MB/s），是环境抖动。

**水位唯一确定的效果，是让页面侧的数字更假**：水位从 1 MB 提到 4 MB 后，页面侧「本地排空」
从 865–1937 ms 掉到 66–102 ms（背压触发从 7–8 次降到 1 次），而 Host 实测吞吐纹丝不动。
水位只是让数据更快地堆在本地缓冲区里，并没有让对端收得更快——这恰好是 3.1 那个口径陷阱的放大版。

### 3.4 多 DataChannel 并行：没有稳定收益

| 通道数 | 配置 | 三轮总吞吐 (MB/s) | 平均 |
| --- | --- | --- | --- |
| 1 | 64 KB / 4 MB | 9.6 / 10.9 / 4.8 | 8.4 |
| 2 | 64 KB / 4 MB | 11.9 / 8.1 / 6.0 | 8.7 |
| 4 | 64 KB / 4 MB | 5.6 / 9.2 / 4.7 | 6.5 |
| 4 | 16 KB / 1 MB | 6.3 / 2.9 / 5.5 | 4.9 |

单通道在 64 KB / 4 MB 下的全部 11 轮测得 2.8–10.9 MB/s（平均 6.1），2 条通道的 8.7 和
4 条的 6.5 都落在这个区间内——**多通道没有可复现的收益**，4 条还低于单通道平均值。

原因：**同一个 PeerConnection 上的所有 DataChannel 共享同一条 SCTP 关联**，
底层收发本来就是串行的，多开通道只是把同一份带宽切成几份，还多出调度开销。

结论：**不要为了提速去开多通道**。多通道该用在需要逻辑隔离的地方（比如控制消息和业务数据分流），
不是用来加带宽的。

### 3.5 最终数字

| 方向 | 实测（单机 loopback） |
| --- | --- |
| 上行 客户端→Host | **3–6 MB/s（约 24–48 Mbps）** |
| 下行 Host→客户端 | **21–31 MB/s（约 170–250 Mbps）** |

下行是上行的 5 倍以上，这个不对称很稳定。原因大概率在 werift 的接收路径：
收数据要经过 JS 层的 SCTP 拆包、DTLS 解密、事件派发，全在单线程上跑（实测 CPU 峰值 109%，单核打满）；
发送方向的开销小得多。

## 四、必须配 STUN，这不是可选项

Chromium 默认用随机主机名（`xxxx-xxxx.local`）隐藏本地 IP，而 werift 不解析 mDNS。
不配 STUN 时，Host 连不上浏览器的 host 候选，只能等对方先发包、从源地址反推一个 `prflx` 候选，
局域网直连会退化成单向被动路径。

**所有客户端都必须配 STUN**。SRFLX（经 STUN 反射出的公网地址）和 RELAY（TURN）候选不带 mDNS 混淆。

另外还有一条运营商侧的现实：NAT 穿透不可能 100% 成功（对称 NAT、CGNAT、企业防火墙），
**TURN 兜底必须有**。

## 五、其它已经踩过的坑

1. 应答方不能显式调 `setLocalDescription("answer")`，会让进程直接 abort。libdatachannel 会自动生成 answer。
2. **PeerConnection 必须隔离到独立进程**：上面那个 abort 是未捕获的 C++ 异常，会连带杀掉整个 Node 进程。
3. 跨设备测试必须 HTTPS，浏览器只在安全上下文里允许 WebRTC。
4. 移动端（Tauri 用系统 WebView）没有额外负担：DataChannel 不碰麦克风摄像头，
   绕开了 iOS `AVAudioSession` 那一堆坑。

## 六、对现有方案的影响

### 6.1 可以删掉的

- 自研端到端加密整套（658 行 × 3 份副本）
- challenge proof、公钥指纹登记与校验
- base64 + JSON 信封（顺带省掉约 33% 的流量放大）
- 会话实例亲和（WebRTC 连接建立后是点对点，不需要会话粘在某个中继实例上）
- 三级域名作为业务入口的跳转链路

### 6.2 要新增的

- 信令服务器（只转发 SDP / ICE，轻量）
- STUN 服务（可自建也可用现成的）
- TURN 服务（coturn，兜底用）
- Host 侧 werift 接入层，且要跑在独立进程里

### 6.3 要改的

- 计量：P2P 打通后流量不经过服务器，网络层计量不再可能。
  这直接推翻了「按流量计费」的可行性，见下面第七节。

## 七、计费模型必须跟着改

**这是本次验证带出来的最大业务结论，不是技术细节。**

P2P 打通后，用户和 Host 之间的数据根本不经过我们的服务器，**网络层拿不到计量数据**。
客户端软件上报的用量天然不可信，用户少报我们也发现不了。

所以：

1. **计费不能再以流量为基准**，改成固定月订阅。
2. 计量本身还有用，但定位从「计费依据」降级为「风控参考」。
3. **TURN 兜底流量仍然产生真实成本**（对称 NAT、CGNAT、企业防火墙用户走 TURN）。
   这部分要单独限速和预算，不能开成无限量。

## 八、还没验证的风险

下面这些**目前一个都没测**，上生产前必须补：

1. **真实网络**：所有数字都来自单机 loopback。真实链路（跨地域、弱网丢包、对称 NAT）下上行只会更慢。
2. **长时间稳定性**：只跑了 20 MB 单次，没跑过连续几十分钟、几百 MB，不知道纯 JS 实现会不会内存泄漏或性能衰减。
3. **TURN 路径**：测的全是 P2P 直连。走 coturn 的吞吐、延迟，以及 coturn 能不能吐出可用的计量数据，都没验。
4. **移动端真机**：桌面浏览器验过，iOS / Android WebView 没验。
5. **信令服务器规模**：demo 里的信令是单机玩具，没有并发、重连、鉴权的生产设计。
