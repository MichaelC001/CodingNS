## 这份文档回答什么

Host 侧要跑一个 WebRTC 接入进程。这份文档定清楚四件事：

1. 进程怎么切、谁负责什么
2. 两个进程之间怎么说话
3. 接入进程崩了怎么办
4. 为什么不能省掉这一层，直接把 werift 塞进主进程

后面 W1.1 直接按这份文档写代码，不再现拍。

## 一句话结论

**主进程只管配置、状态和设置页；werift 的 PeerConnection 全部跑在一个独立子进程里，中间用一条 IPC 通道通信，子进程挂了主进程负责拉起。**

## 一、为什么必须分进程

libdatachannel 已经实测出「未捕获 C++ 异常直接杀进程」。werift 是纯 TypeScript，没有这个问题，但分进程的理由不止这一个：

| 理由 | 说明 |
| --- | --- |
| **故障隔离** | WebRTC 状态机复杂（ICE / DTLS / SCTP 三层），一个连接进入异常态不应该带走整个 Host |
| **事件循环保护** | werift 收数据时单核能打满（实测 CPU 峰值 109%），放主进程会直接拖慢所有业务接口 |
| **内存可控** | 实测 werift 稳定在 268 MB 量级，独立进程可以单独设上限、单独回收 |
| **可重启** | 网络策略调整、实现升级，重启接入进程即可，不用重启整个 Host |

第三条尤其重要：**接入进程是 Host 里唯一会持续吃 CPU 的网络组件**，它必须有一个能被单独掐掉的边界。

## 二、进程划分

```text
┌──────────────────────────────────────────────┐
│ 主进程（apps/host 现有 Node 进程）              │
│                                              │
│  - 实例级配置读写（InstanceRelayTunnelConfig）  │
│  - 状态机与设置页接口                          │
│  - 绑定 / 解绑 / 启停                          │
│  - 用量与链路类型上报                           │
│  - 子进程生命周期：启动、监控、拉起、关闭         │
│  - TaskManager 注册所有后台任务                 │
└──────────────────┬───────────────────────────┘
                   │ IPC（父子进程，JSON 消息）
┌──────────────────▼───────────────────────────┐
│ 接入进程（新增）                                │
│                                              │
│  - werift PeerConnection（每个客户端一条）      │
│  - 信令 WebSocket 客户端（连信令服务器）         │
│  - DataChannel 二进制收发                       │
│  - 把业务消息转成对本地 127.0.0.1:<port> 的请求   │
│  - 把本地响应写回 DataChannel                   │
└──────────────────────────────────────────────┘
```

**边界划在哪：**
接入进程只认「一条 PeerConnection 怎么建、怎么收发」，**不碰任何持久化**。
配置、绑定关系、状态落库全在主进程。这样接入进程可以随时被杀掉重启，不会丢状态。

## 三、IPC 协议

用 Node 的 `child_process.fork`，走标准 IPC 通道。消息是 JSON，两边约定一组固定的 `type`。

### 3.1 主进程 → 接入进程

| 消息 | 作用 |
| --- | --- |
| `configure` | 下发当前配置：信令地址、凭据、ICE 配置、本地转发目标 |
| `shutdown` | 优雅退出（先关所有 PeerConnection，再退出） |
| `ping` | 健康检查 |

### 3.2 接入进程 → 主进程

| 消息 | 作用 |
| --- | --- |
| `ready` | 启动完成，可以收 `configure` |
| `state` | 状态变化：`signaling_connecting` / `waiting_for_peer` / `running_p2p` / `running_relay` / `error` |
| `session` | 有客户端接入 / 断开，带上链路类型（p2p / relay） |
| `usage` | 用量上报（降级为风控参考，见 design.md 第 11 节） |
| `error` | 错误，带可读原因 |
| `pong` | 健康检查应答 |

### 3.3 硬规则

- **IPC 消息里不传业务数据**。业务字节只在 DataChannel 里走，IPC 只传控制信号。
  否则接入进程省下来的 CPU 又通过 IPC 序列化还回去了。
- 状态上报要合并、限频。不允许每收一个包就发一条 IPC。
- 主进程收到 `state` 只更新状态，不触发重活。

## 四、崩溃与拉起

### 4.1 监控

主进程持有子进程句柄，监听 `exit` 和 `error` 两个事件。

### 4.2 拉起策略

- 意外退出（非 `shutdown` 触发的）：自动拉起
- 拉起要有退避，不能失败就疯狂重启：
  首次立即重试，之后按 1s / 2s / 4s / 8s / 16s 递增，**上限 30s**
- 连续失败达到阈值（建议 5 次）后停止自动拉起，状态置 `error`，
  把原因写进 `lastError` 让设置页能看到，等用户手动重试

**这条是硬要求**：不能出现「进程起不来 → 疯狂重启 → 把机器打满」的循环。

### 4.3 拉起后要做什么

接入进程重启后是干净的，主进程必须**重新下发一次 `configure`**，
不能假设子进程还记得之前的配置。

### 4.4 和 TaskManager 的关系

按 `spec001.2` 后台任务规范：

- 接入进程的启动 / 监控 / 拉起注册成后台任务，`taskType` 用 `webrtc.peer_supervise`
- 状态刷新用 `relay_tunnel.state_refresh`
- 用量上报用 `relay_tunnel.usage_report`
- **不允许**在主进程里另起一套私有的 `inflight`、`timer`、重试队列

## 五、接入进程内部怎么组织

一个接入进程内可以有多条 PeerConnection（每个客户端一条），共享：

- 一条到信令服务器的 WebSocket
- 一份 ICE 配置
- 一个本地转发目标地址

但**每条 PeerConnection 各自独立**：

- 独立的状态机
- 独立的 DataChannel
- 一条出问题只关它自己，不影响别的客户端

**明确不做多进程池**：单进程足够支撑第一阶段的目标连接数，
真到 CPU 扛不住的时候再评估，不要提前复杂化。

## 六、明确不做什么

- 不做多进程池 / 进程池调度
- 不做接入进程的热更新（升级就是重启）
- 不把业务数据塞进 IPC
- 不在接入进程里读写 SQLite 或任何持久化
- 不做「接入进程崩了但假装没崩」的兜底（崩了就是崩了，状态必须如实上报）

## 七、怎么验证

W1.1 / W1.4 落地后，按下面几条验收：

1. **进程隔离**：`kill -9` 接入进程，确认主进程存活、业务接口不受影响、接入进程被自动拉起
2. **状态如实**：接入进程挂掉期间，设置页状态不是 `running_*`
3. **退避生效**：人为让接入进程启动即退出，确认重试间隔递增、达到阈值后停止并置 `error`
4. **配置重下发**：接入进程重启后，确认自动重新下发 `configure`，不用人工干预
5. **IPC 不传业务数据**：抓 IPC 消息，确认只有控制信号
6. **CPU 边界**：压一条连接打满带宽，确认主进程事件循环没有被拖慢
