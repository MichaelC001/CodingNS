## 已经验证过的事实（直接采信，不要重复验证）

- Node 侧 WebRTC 有两套可选实现，各有硬伤，**选型尚未拍板**：
  * node-datachannel（libdatachannel）：上行快（16–58 MB/s），但浏览器向 Host 传 5 MB 时，
    约 40% 概率 ICE 从 completed 直接跳到 failed，重试稳定复现；上游 issue #375 是同类数据丢失问题。
  * werift：上行慢（2.5–7.3 MB/s，单核打满），但 11/11 稳定通过，下行约 26.8 MB/s 可用，
    内存稳定在 268 MB。纯 TypeScript，出问题可以自己打补丁。
- 分片大小、背压水位这些参数调优，对上行没有稳定收益，
  之前看到的「快 2.7 倍」是单批次连续测试被同一段机器负载染色造成的假象。不要再花时间调参。
- 多 DataChannel 并行没有吞吐收益：同一条 PeerConnection 上的通道共享同一个 SCTP 关联，底层本来就是串行。
- 发送侧报的「上传完成」耗时不等于真实吞吐（只统计写进本地缓冲），必须用接收侧打点。
  这个坑的细节写在验证结论文档 3.1 节。
- Chromium 默认会把 host 候选做 mDNS 混淆（xxxx.local），libdatachannel 解析不了，
  所以客户端侧 STUN 是必需项，不是可选优化。

## 这份提示词的来历

几个关键判断是在实测里反复翻盘之后才定下来的，写在这里免得后面又被推翻：

| 判断 | 怎么来的 |
| --- | --- |
| 调参没用 | 先是单批次测出「64 KB + 4 MB 快 2.7 倍」，交替重跑后差异消失，确认是负载染色 |
| 多通道没用 | 2 通道打平、4 通道反而更差，原因是共享同一条 SCTP 关联 |
| 发送侧数字不可信 | 页面报 88 MB/s，Host 侧实测只有 8.2 MB/s，差十倍以上 |
| libdatachannel 不稳 | 多批次累计 3/16 通过，失败时 ICE 从 completed 直接 failed，无 SCTP 报错 |
| werift 稳但慢 | 11/11 通过，上行 2.5–7.3 MB/s，下行约 26.8 MB/s |
