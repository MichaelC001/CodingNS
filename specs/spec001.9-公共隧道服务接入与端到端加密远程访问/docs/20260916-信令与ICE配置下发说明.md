# 信令与 ICE 配置下发

日期：2026-09-16
对应任务：`tasks.md` W3.1、W3.3

## 这份文档回答什么

WebRTC 连接建立前，Host 和客户端各自要知道什么、从哪拿、谁能拿到。写完这份，
后面接 Host 侧和客户端时不用再去翻代码猜。

## 一、连接方向为什么固定成「客户端 offer / Host answer」

客户端是访问的发起方，Host 是被动等待方。

反过来做的话，Host 要为每个潜在客户端维护连接状态，Host 侧复杂度会失控；
而且客户端在 NAT 后面时，让 Host 主动发起连接没有意义。

所以：

- **客户端**：拿到 client 票据 → 连信令 → 建 PeerConnection → 发 offer
- **Host**：拿到 host 票据 → 连信令 → 等 offer → 回 answer

## 二、一次完整建连的步骤

```text
客户端                         控制面                        信令服务                      Host
  |                              |                              |                          |
  |-- POST /api/v1/relay/signaling/ticket (tunnelDomain) ------>|                          |
  |<-- ticket + iceServers + hostDtlsFingerprint ---------------|                          |
  |                              |                              |<-- 同样接口 (bindingId) --|
  |                              |                              |--- ticket -------------->|
  |-- WS /signal?ticket=... ---------------------------------->|<-- WS /signal?ticket=... -|
  |<-- registered / peer-ready --------------------------------|-- registered / peer-ready |
  |-- offer -------------------------------------------------->|--- offer --------------->|
  |<-- answer -------------------------------------------------|<-- answer ----------------|
  |<-- candidate (双向) ---------------------------------------|-- candidate (双向) ------>|
  |                              |                              |                          |
  |========== 之后业务数据走 WebRTC DataChannel，不再经过信令服务 ==========|
```

关键点：**第 6 步之后信令服务就没事了**。业务数据走 DataChannel，端到端加密。

## 三、票据怎么设计

### 3.1 形状

`<base64url(payload)>.<base64url(hmac-sha256)>`，和 JWT 类似，但没引入第三方库。

payload 里只有：

| 字段 | 说明 |
| --- | --- |
| `role` | `host` 或 `client` |
| `bindingId` / `tunnelDomain` | 连的是哪个绑定 |
| `accountId` | 属于哪个账号 |
| `sessionId` | 客户端才有；Host 为 `null`。Host 靠它区分不同客户端 |
| `jti` / `issuedAt` / `expiresAt` | 票据 id 与有效期 |

### 3.2 为什么不用 JWT 库

只需要 HMAC + 过期时间，不需要算法协商、不需要公钥。引一个库反而多一层依赖。

### 3.3 为什么控制面和信令服务要共用一份实现

两边各写一份的话，签和验一旦不一致，问题只在生产环境暴露。
所以实现在 `packages/shared-contracts/src/signaling-ticket.ts`，通过子路径
`@codingns-proxy/shared-contracts/signaling-ticket` 导出。

**单独开子路径的原因**：这个文件依赖 `node:crypto`，不能被打进浏览器包。
console-web 只从主入口 `"."` 引类型，不会被牵连。

### 3.4 有效期

默认 60 秒。够建立一次 WebRTC 连接，泄漏窗口也小。
票据是一次性的，过期后要重新走控制面。

### 3.5 票据能保护什么、不能保护什么

- **能**：证明「这张票是我们签的、没过期、属于哪个绑定和角色」
- **不能**：保密。票据内容是可读的 base64，任何人都能解出来

这没关系——票据里没有任何密钥材料，信令服务本来也不该看到业务明文。

## 四、ICE 配置怎么下发

控制面在票据接口里一起返回：

```json
{
  "iceServers": [
    { "urls": "stun:stun.l.google.com:19302" },
    {
      "urls": ["turn:turn.example.com:3478"],
      "username": "1790000000:acct_xxx",
      "credential": "base64-hmac"
    }
  ],
  "iceTransportPolicy": "all",
  "hostDtlsFingerprint": "SHA-256 xx:xx:..."
}
```

### 4.1 STUN 恒定下发

**客户端侧 STUN 是必需项，不是可选优化。** Chromium 会把 host 候选做 mDNS 混淆
（`xxxx.local`），werift 解析不了，不配 STUN 局域网直连会退化成单向被动路径。
详见验证结论第四节。

### 4.2 TURN 用临时凭据

用 coturn 的 REST API 约定：

```text
username   = <过期时间戳>:<账号标识>
credential = base64(hmac-sha1(username, sharedSecret))
```

这样控制面不需要存长期密码，也不需要为每个用户建 TURN 账号。
客户端拿到的凭据自带过期时间，coturn 用同一把共享密钥验。

`username` 里的冒号是分隔符，所以账号 id 里的冒号会被替换成下划线，否则过期时间会解析错位。

### 4.3 TURN 没配就不下发

如果没配 `CODINGNS_PROXY_TURN_URLS` 或 `CODINGNS_PROXY_TURN_SHARED_SECRET`，
就不下发 TURN 候选。

**这是有意的**：给一个连不上的 TURN 地址，只会让客户端多等一轮超时。

### 4.4 传输策略开关

`CODINGNS_PROXY_FORCE_TURN_BY_DEFAULT`：

- `false`（默认）：`iceTransportPolicy: "all"`，局域网 / metro 允许直连
- `true`：`iceTransportPolicy: "relay"`，强制走 TURN

固定订阅模式下默认允许直连（省带宽成本），跨网场景按需打开。

**遗留**：目前只有全局开关，还没有按账号粒度控制。等 W5 订阅模型落地后一起补。

## 五、环境变量

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `CODINGNS_PROXY_SIGNALING_HOST` | `127.0.0.1` | 信令服务监听地址 |
| `CODINGNS_PROXY_SIGNALING_PORT` | `4330` | 信令服务端口（本地栈用 18085） |
| `CODINGNS_PROXY_SIGNALING_PUBLIC_BASE_URL` | 无 | 对外信令地址，下发给客户端 |
| `CODINGNS_PROXY_SIGNALING_MAX_CLIENTS_PER_BINDING` | `8` | 单绑定并发客户端上限 |
| `CODINGNS_PROXY_SIGNALING_DEBUG_LOGS` | `false` | 信令调试日志 |
| `CODINGNS_PROXY_STUN_URLS` | `stun:stun.l.google.com:19302` | 逗号分隔 |
| `CODINGNS_PROXY_TURN_URLS` | 空 | 逗号分隔，空则不下发 TURN |
| `CODINGNS_PROXY_TURN_SHARED_SECRET` | 无 | coturn `static-auth-secret` |
| `CODINGNS_PROXY_TURN_CREDENTIAL_TTL_SECONDS` | `3600` | TURN 临时凭据有效期 |
| `CODINGNS_PROXY_FORCE_TURN_BY_DEFAULT` | `false` | 是否强制走 TURN |

控制面和信令服务必须共用同一把 `CODINGNS_PROXY_INTERNAL_RELAY_API_KEY`，
否则票据验不过。

## 六、信令服务器能看到什么

| 能看到 | 看不到 |
| --- | --- |
| 哪个账号、哪个绑定、哪个角色 | 业务明文 |
| SDP 与 ICE 候选 | DTLS 密钥 |
| 何时建立、何时断开、有几个客户端 | 数据内容 |

**信令服务器不解析 SDP 内容**，只做转发。内容是否合法由两端自己的 WebRTC 栈判断。

## 七、房间模型

- 一个绑定 = 一个房间
- 一个房间最多一个 Host，多个客户端
- 同一绑定的 Host 重连会顶掉旧连接（避免旧连接僵死导致 Host 永远上不来）
- 同一 `sessionId` 的客户端重连也会顶掉旧的（支持断线重试）
- 房间在 Host 和所有客户端都断开后才回收；只有 Host 断开时房间保留，等 Host 回来

## 八、怎么验证

```bash
cd apps/codingns-proxy

# 单元与接口测试
pnpm --filter @codingns-proxy/shared-contracts test   # 票据签发/校验
pnpm --filter @codingns-proxy/relay-signaling test    # 房间路由 + WebSocket 端到端
pnpm --filter @codingns-proxy/control-api test        # 票据接口 + TURN 凭据

# 真实链路联调
pnpm local:stack:start
# 绑定 Host 后换票据，两个 WebSocket 连 /signaling/signal，验证 offer/answer 转发
```

覆盖的场景：票据过期 / 篡改 / 换密钥 / 无票据拒绝、Host 不在线明确报错、
角色越权（客户端不能发 answer、Host 不能发 offer）、同绑定 Host 重连顶号、
客户端数超上限、在线快照、别人的绑定换不到票。
