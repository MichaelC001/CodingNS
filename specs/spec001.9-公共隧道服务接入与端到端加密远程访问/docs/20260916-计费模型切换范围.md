# 计费模型切换范围：从「按流量」改成「固定订阅」

日期：2026-09-16
对应任务：`tasks.md` W0.3
依据：`design.md` 第 11 节、`docs/20260916-WebRTC承载层验证结论.md`

## 这份文档回答什么

承载层换成 WebRTC 以后，原来那套「流量钱包 + 扣量 + 用完断流」的计费方式不成立了。
这份文档把要改的表、接口、页面、配置，以及存量数据怎么处理，一次列清楚。
W5 照着做，不用再回头翻代码找。

**这一步只做范围确认，不写迁移脚本、不改代码。**

## 一、为什么必须换

一句话：**服务端失去了「按流量计量」的能力。**

原来的链路里，`relay-edge` 是唯一的通道，每个会话双向走了多少字节它都数得到，
所以能扣量、能断流、能对账。

换成 WebRTC 之后：

- **P2P 直连的会话，字节根本不经过我们的服务器。** 客户端和 Host 之间点对点传输，
  中间没有一台机器看得见流量。这不是「暂时没做统计」，是物理上看不到。
- **只有走 TURN 的那部分，coturn 数得到准确字节数。** 但走不走 TURN 取决于双方网络，
  同一个用户今天直连、明天走 TURN，被扣的量完全不一样。

如果继续按流量收费，会出现很荒唐的结果：

- 家里网络好、天天直连的用户，用量永远是 0，等于免费用
- 公司网络差、被迫走 TURN 的用户，同样的使用强度被扣得最多
- 用户完全无法预测这个月要花多少钱

所以计费口径必须换成**与传输路径无关**的东西——也就是「一段时间内可以用」的固定订阅。

## 二、现状盘点

### 2.1 要动的数据表

位置：`apps/codingns-proxy/apps/control-api/src/database-migrations.ts`

| 表 | 现在干什么 | 换成订阅后怎么处置 |
| --- | --- | --- |
| `traffic_wallets` | 账号级流量账本：`granted_bytes` / `used_bytes` | **停止作为限额依据**。保留表结构做一个迁移周期，字段改成只读展示；确认无引用后再删 |
| `traffic_orders` | 流量包订单：`package_id` / `granted_bytes` / `status` / `paid_at` | **改语义**：`granted_bytes` 不再是主体，改成订阅周期与套餐 id。存量行保留，新订单不再写 `granted_bytes` |
| `traffic_grants` | 每次发放流量的明细 | 改成「订阅周期发放记录」，或者直接停用 |
| `activation_codes` | 激活码，兑换流量 | **要决策**：是改成兑换订阅时长，还是直接停发。见第四节 |
| `payment_events` | 支付回调幂等表 | 不动，继续用 |
| `order_recovery_actions` | 订单人工补偿动作 | 不动，继续用 |
| `relay_usage_events` | 逐会话的用量事件（relay-edge 上报） | 保留但**只作展示与风控**，不再驱动扣费。P2P 会话这里不会有数据，这是预期行为 |
| `relay_usage_daily_summaries` | 按天聚合用量 | 同上，保留 |
| `relay_usage_retention_settings` | 用量数据保留策略 | 不动 |
| `tunnel_bindings.session_rate_limit_bytes_per_second` | 单会话限速 | **保留**。限速属于风控，不属于计费，WebRTC 下仍然需要 |

需要**新增**的表（W5.1 落地时建）：

- `subscriptions`：账号、套餐 id、周期起止、状态（`active` / `expired` / `canceled`）、续费时间
- `subscription_plans`：套餐定义（周期、价格、并发连接数、是否允许走 TURN）

### 2.2 要动的接口

位置：`apps/codingns-proxy/apps/control-api/src/app.ts`

| 接口 | 现状 | 处置 |
| --- | --- | --- |
| `GET /api/public/traffic-packages` | 返回流量包列表 | 改成返回订阅套餐列表，路径建议同步改名 |
| `GET /api/v1/traffic-wallet/me` | 返回钱包余额 | 改成返回订阅状态（是否有效、到期时间、套餐名） |
| `GET /api/v1/traffic-wallet/grants` | 返回发放明细 | 改成订阅周期明细，或下线 |
| `POST /api/v1/activation-codes/preview` | 激活码预览 | 跟着 `activation_codes` 的决策走 |
| `POST /api/v1/activation-codes/redeem` | 激活码兑换 | 同上 |
| `GET /api/v1/orders` | 订单列表 | 保留，展示字段调整 |
| `GET /api/internal/ops/orders/:orderId/reconciliation` | 订单对账 | 保留 |
| `POST /api/internal/ops/orders/:orderId/replay-grant` | 人工补发流量 | 改成人工补发订阅周期 |
| `POST /api/internal/relay/sessions/authorize` | 授权会话，**余额为 0 时返回 `QUOTA_EXHAUSTED` 拒绝** | **必须删掉这段拒绝逻辑**，改成校验订阅是否有效 |
| `POST /api/internal/relay/sessions/consume` | 上报用量扣减 | 降级为风控数据入库，不再扣减任何东西 |
| `POST /api/v1/relay/signaling/ticket` | 换信令票据 | 加一道订阅状态校验：订阅过期不许换票 |

**这里有一条必须做对的**：`/api/internal/relay/sessions/authorize` 里的 `QUOTA_EXHAUSTED` 断流
（`app.ts` 第 1983 行附近）是「用完就断」的执行点。改成订阅后，只要订阅有效就必须放行。

### 2.4 要动的配置

| 配置 | 处置 |

| `CODINGNS_PROXY_DEFAULT_TRAFFIC_BYTES` | 删除。新账号不再自动送流量 |

| `CODINGNS_PROXY_TURN_*` | 保留，不动 |

### 2.5 用量链路变成什么样

```text
P2P 直连会话  →  服务端完全看不到流量  →  只有客户端上报的估算值（风控参考）
TURN 中继会话 →  coturn 数得到准确字节  →  风控参考 + 成本核算
```

两条链路都**不再驱动扣费**。用量数据的用途收敛成两件事：

1. 控制台给用户看「这个月大概用了多少」
2. 异常检测：某个账号用量突然暴涨时告警

## 三、换成什么

### 3.1 模型

- **套餐（plan）**：名字、周期（月/年）、价格、允许的并发连接数、是否含 TURN 中继
- **订阅（subscription）**：账号买了一份套餐，有起止时间；到期前可续费
- **订单（order）**：一次付款记录，付成功后延长订阅周期

### 3.2 授权规则（授权接口判断依据）

客户端换信令票据时校验：

1. 账号有 `active` 状态的订阅 → 放行
2. 订阅已过期 → 返回明确的「订阅已到期」，让客户端能提示用户续费
3. 没有订阅 → 同样拒绝，提示去购买

**不再有「流量用完了」这种拒绝理由。**

### 3.3 并发上限

套餐里的并发连接数在这里生效：`relay-signaling` 已经有
`CODINGNS_PROXY_SIGNALING_MAX_CLIENTS_PER_BINDING`（默认 8）。
W5.1 之后这个上限要能从订阅套餐读，而不是全局写死。

## 四、存量数据怎么处理

这是最容易出事的地方，逐条定：

| 存量对象 | 处置 |
| --- | --- |
| 已购买但没用完的流量包订单 | **给这些账号按剩余额度折算一段时间的订阅**（比如剩余流量 ≥ 一定量就送 1 个月）。折算规则要写死并公告，不能静默吞掉 |
| `traffic_wallets` 里还有余额的账号 | 同上，折算依据 |
| 已经发出去还没兑换的激活码 | 二选一：**(a)** 改成兑换订阅时长，继续可用；**(b)** 停止兑换并给持码人退款通道。**推荐 (a)**，改动小、用户无感 |
| 已过期的历史订单 | 原样保留，只做展示，不参与新逻辑 |
| 历史用量明细 | 原样保留，控制台标注「历史流量数据」 |

**迁移必须是一次性脚本 + 可重复执行（幂等）**，跑之前先备份。
不允许「一边跑一边改规则」。

## 五、明确不做什么

- 不做团队套餐 / 多人共享订阅
- 不做按用量分档的阶梯价
- 不做自动续费的扣款重试（先只做「到期提醒 + 手动续费」）
- 不重写 Paddle 接入方式，只改商品语义
- 不删历史数据，只停用旧逻辑

## 六、怎么验证

W5 落地后按这几条验收：

1. **订阅有效的账号能连**：买一份订阅，换票据、建连、跑业务，全通
2. **订阅过期的账号连不上，且提示可读**：把订阅时间改成过去，确认拒绝理由不是「流量耗尽」
3. **用量不再影响可用性**：人为把用量数据刷到很大，确认连接不受影响
4. **存量折算正确**：拿一个还有余额的老账号跑迁移脚本，确认折算出的订阅周期符合规则；重复跑一次，确认不会重复发放
5. **控制面测试**：`pnpm --filter @codingns-proxy/control-api test`
6. **页面走查**：控制台不出现「流量包」「余额」这类旧词，也不出现 `granted_bytes` 这种字段名

## 七、给 W5 的落地顺序

1. W5.1：建 `subscriptions` / `subscription_plans` 两张表 + 授权接口改成看订阅
2. W5.2：用量链路降级成风控口径（去掉扣减、改标注）
3. W5.3：TURN 限速与告警接上（`session_rate_limit_bytes_per_second` + coturn 配额）
4. 最后一步才做存量折算脚本和公告

前两步做完，系统就已经能正常跑；后两步是运营层面的收尾。
