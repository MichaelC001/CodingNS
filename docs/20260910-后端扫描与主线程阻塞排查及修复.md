# 3002 后端扫描与主线程阻塞排查及修复

## 结论

性能问题存在，但不能把所有等待都归因于 Host 主线程持续阻塞。实测同时发现了 helper 缓存反复丢失、Codex 外部元数据查询无整轮预算、无关 Kimi 正文解析、主线程重复 SQLite 写入，以及 3009 实例的资源竞争。

本次修改仅作用于当前仓库及其已有开发监听进程，没有停止或升级 3009，也没有删除遗留进程或用户数据。开发监听器在源码和 core 编译结果更新时自动重载，PID 随之变化。

## 证据与实际修复

### Codex / Kimi 扫描

- 原 helper 只保留一个 `workspaceDiscoveryRuntime`。扫描、单 provider 历史和标题读取使用不同配置 key，来回切换就丢掉 adapter 内部文件指纹缓存和历史 checkpoint（增量读取位置）。现在按 provider 自身配置复用 adapter，最多保留 32 项；Claude 额外目录变化不会清除 Kimi/Codex 缓存。
- Kimi 原来解析完完整消息才排除其他工作区。现在先读取轻量 state 和目录归属映射，再决定是否需要读正文。
- Codex 每轮都可能启动 app-server 查询线程，并串行补读父线程。现在增强查询共享 3 秒时间预算，超时关闭 transport，继续使用本地索引；增强结果和失败保留 5 秒，改名、归档、删除会主动使相关缓存失效。这个预算不代表整轮文件扫描保证在 3 秒内完成。
- 整轮结果缓存命中原来会重放旧诊断成本。现在命中时本次扫描耗时、扫描数、解析数和读取字节数为零，不修改原始结果。此前历史记录中的累计字节数包含这类重复记账，不能直接等同于实际磁盘 I/O。

本机只读复测：

| 场景 | 结果 |
| --- | --- |
| Kimi，CodingNS 工作区，首次扫描 | 46 个候选，5 ms，正文解析 0 |
| Kimi，同 adapter 再扫描 | 1 ms，46 个文件指纹命中，正文解析 0 |
| Codex，不传已知会话的冷扫描 | 83 条会话，约 6.1 秒，诊断正文规模约 380 MB |
| Codex，随后整轮缓存命中 | 约 1 ms |

以上不是相同负载下的严格前后性能对照。Codex 大目录冷扫描仍有成本；本次修复重点是缓存复用、外部查询预算及重复解析，冷扫描在 helper 中执行。

### SQLite 主线程写入

对重载后的 3002 进程做了 20 秒 V8 采样，定位到：

- `RelayTunnelRuntimeEdgeAdapter.runSupervisor → InstanceRelayTunnelRepository.upsertStatus`：采样累计约 30 ms。
- `ChannelPollingService.runPollTask → ChannelAccountRepository.update`：采样累计约 22 ms。
- `PluginSchedulerService → PluginRegistryService.listPlugins → syncPluginsFromDisk`：采样累计约 63 ms。

这些是本次采样累计值，不是单次调用耗时，也不能证明与此前每一次阻塞完全同源。临时 inspector（调试检查器）在采样后已关闭。

修复内容：

- 隧道重复的同一失败状态最多每 30 秒落一次失败心跳；状态、流量、错误变化及恢复立即写入。
- 渠道重复的同一轮询失败同样限频；网络轮询不暂停，成功结果中的消息及游标仍立即保存。
- 会话状态实际未变时不因 `updated_at` 变化重写快照。
- 插件清单内容和安装位置未变时不重复写定义与注册审计记录。当前同步磁盘检查仍保留。
- 业务 SQLite 查询超过 100 ms 时输出 `[sqlite.slow]`，包含操作、表名和调用栈；按操作/表/方法限频，不输出 SQL 正文和绑定参数。它覆盖 `run/get/all`，不是完整数据库事务剖析器。

### Grok 历史与订阅

- Host 历史接口通过现有 `session.history_delta_read` 任务下沉读取；没有另建 inflight 或队列。
- helper 返回真实 `updates.jsonl` 路径，订阅复用已有来源协调器：文件事件只标脏，经静默窗口合并后读取，替代 Host 每 300 ms 拉历史。
- 按 inode、size、mtime、ctime 缓存解析结果；最多 8 项，原文件字节预算 16 MiB，单个超过 8 MiB 的文件不常驻解析缓存。变化后仍进行完整解析，不把它宣称为字节级增量解析。
- 会话目录定位缓存有数量上限；缺失目录负缓存 1 秒，允许稍后落盘恢复。
- 修正前后向分页游标；追加超过一页时逐页补齐。文件截断/尾部变化会核对尾页，Host 按消息签名去重。
- 无时间戳旧消息使用稳定的文件创建时间作为回退，避免每次重读生成新时间而重复广播。
- `GROK_SESSION_NOT_FOUND` 映射为 `404 / PROVIDER_SESSION_NOT_FOUND`，不再误报通用 502。

## 双实例资源竞争

3002 使用仓库内 `apps/host/data/host/host.sqlite`；3009 使用 `/Users/jackson/.codingns/host.sqlite`。它们没有争用同一个 Host SQLite 文件，但会竞争 CPU、内存、磁盘及共享 provider 本地文件。

本轮一次进程树快照：

| 端口 | 进程数 | CPU 合计 | RSS 合计 |
| --- | --- | --- | --- |
| 3002 | 9 | 约 4.2% | 347 MiB |
| 3009 | 27 | 约 223.6% | 1717 MiB |

CPU 合计可以超过 100%，以上为瞬时快照。3009 有两个 Codex 子进程分别接近单核满载。当前仓库修复不会自动更新该已安装实例，不能据此声称整机资源竞争已经消失。
